## 2026-07-23 — Emote: `max_concurrent_loopers` cap removed; stale dashboard copy from the same day's default-loop flip fixed across all 5 locales

## 2026-07-23 — Emote: Loop flipped to on-by-default and merged into emote-on-say; numbered emote trigger built

Two changes to `EmoteEngine` (`workers/runtime/catalog/emote.py`), by request:

**Loop is now the default behavior of a bare emote word, not a separate opt-in command.** `loop.enabled` schema default flipped `false` → `true`, `loop.interval_s` default `8` → `5` (`packages/schemas/emcee/v1.json`). Behaviorally, a bare word/alias/number match now starts the same repeating loop `loop <emote>` always did — both paths call a new shared `_start_or_switch_loop` so they share one cooldown/cap/task-state (alternating between "macarena" and "loop macarena" can't be used to dodge `loop.cooldown_s`). Turning `loop.enabled` off restores the original one-shot-per-say behavior verbatim (the `Doing "Macarena"!` whisper from earlier today, `emote_on_say.cooldown_s`, etc.) — it's a fallback, not a removed feature. The explicit `loop <emote>` prefix still parses and still no-ops when `loop.enabled` is off; kept mainly so existing copy/muscle memory doesn't break, since it's no longer the only way in.

This inverts the launch-time rate-limit posture: emote-on-say's steady state was "cheap, one action per trigger" (specs/bots/emote.md); now the *default* path for the fleet's single most common trigger is a sustained per-user task running up to `max_duration_s` (30 min). `max_concurrent_loopers` (still 3 by default, not changed) now gates the room's primary interaction, not an opt-in extra — flagged in the spec as worth revisiting once there's real usage data, not changed speculatively here since it wasn't asked for. The bare-trigger/normal-chat collision risk noted at launch ("hello" → wave) is correspondingly higher now that a collision means a 30-minute loop, not one wave — also flagged, not resolved.

**Numbered emote trigger** (this was on the spec's "explicitly deferred" list — `say 1-100`): `EmoteCatalog.resolve` now treats all-digit text as a 1-based index into `EmoteCatalog.all()`'s fixed order (`by_position`), so "5" triggers whatever is 5th in that list — same order the `emotes` whisper command shows, which now numbers its entries (`1. Macarena, 2. Hello, ...`) specifically so a player has something to read the number off of. Flows through every existing `resolve()` call site for free (`all 5`, `loop 5` both work too). Confirmed none of the 232 catalog entries have a purely-numeric id/name/alias that this could shadow. → `specs/bots/emote.md`

Follow-up to the same day's local-dev incident (entry directly below this one): fixing the immediate `.env`-loading bug raised the more general question — if the supervisor process dies or never starts for *any* reason (bad env var, an unhandled exception before `Supervisor.run()`, the container failing to come up at all), does anything ever notice? Answer was no. The existing crash-loop alert (`db/instance-alerts.ts`, `specs/04-bot-runtime.md`'s "Instance crash-loop" row) only fires from *inside* the supervisor's own reconcile loop — it detects one tenant's bot failing repeatedly while the process is alive and running. A supervisor that never reaches that loop produces zero rows in `bot_instances`/`instance_events` for anything to key off; every instance just sits wherever it was, silently, for as long as the process stays down. That's exactly the blind spot the incident hit.

**Built:** `workers/runtime/supervisor.py`'s `run()` loop now writes a heartbeat (`db.write_heartbeat` → new `supervisor_heartbeats` table, one row per `supervisor_id`, upserted every `RECONCILE_INTERVAL_S` tick) unconditionally, after `reconcile()` rather than inside it — `reconcile()` has early returns (e.g. no free capacity), and the heartbeat needs to prove the loop itself is alive regardless of which branch it took. A new `/api/cron/supervisor-health` route (every minute — tighter than the crash-loop alert's 5-minute cadence, since this failure mode takes every customer's bot down at once, not just one) reads `MAX(last_seen_at)` across every heartbeat row; if it's missing or older than `HEARTBEAT_STALE_MS` (90s — 9x the normal 10s cadence), it's down. Decision/dedup logic (`lib/supervisor-health.ts`, pure and unit-tested, same split `lib/degraded-alerts.ts` already established) mirrors the crash-loop alert's cooldown shape (30 min between reminders while ongoing) via a new generic `ops_alerts` table (kind-keyed dedup marker, not instance-keyed — there's no instance to key off here), but adds one thing the customer-facing alert doesn't need: a one-time recovery email once the heartbeat is fresh again, so "is it still down" doesn't require staring at silence.

Deliberately **ops-only, never customer-facing** — new `OPS_ALERT_EMAIL` env var (comma-separable), `lib/ops-alert-mailer.tsx` (plain-English templates, no `emails/translator.ts` involved since nobody but us reads these), same throw-in-production/log-in-dev discipline every other mailer in this codebase already uses for a missing `RESEND_API_KEY`. Wired into both deploy paths: `deploy/crontab` (VPS) and `apps/web/vercel.json` (noted inline: per-minute Vercel Cron needs a paid plan, Hobby can't do it — the VPS path has no such ceiling).

**Known, deliberate gap, logged in `specs/04-bot-runtime.md`:** the health check takes `MAX(last_seen_at)` across every `supervisor_heartbeats` row, which is correct for today's single-VPS/single-process deploy (R1, `docs/cost-plan.md`) but wouldn't catch one shard dying while others keep beating, if this ever becomes multi-shard — `shard`/lease-based claiming was already built with that future in mind, this alert wasn't. Also doesn't close the older "nothing monitors the alerting pipeline itself" open question (a broken Resend account or a stopped crontab still degrades to silence) — narrower now, not solved.

Verified: `uv run pytest` (197 passing, including new `write_heartbeat` DB tests and a `Supervisor.run()`-level test proving the heartbeat gets written every tick against a real Postgres pool) and `vitest`/`tsc --noEmit`/`eslint` for the TypeScript half. → `specs/04-bot-runtime.md`

## 2026-07-23 — Bug fix: `workers/runtime/.env` was never actually loaded, silently breaking the documented local-dev supervisor workflow; plus a "Copy diagnostics" dashboard affordance

Reported live: a bot started from the dashboard wasn't appearing in its Highrise room. `bot_instances.desired_state` had correctly flipped to `running` (the dashboard's own job, per `specs/02-architecture.md`'s "billing/dashboard events only ever flip desired_state" split), but nothing was running `workers/runtime/supervisor.py` — the process that actually claims that row and opens the Highrise WebSocket. Running it via the README's own documented path (`cd workers/runtime && uv run python supervisor.py`) crashed immediately with `KeyError: 'DATABASE_URL'`: the module reads `DATABASE_URL`/`TOKEN_SEAL_PRIVATE_KEY` straight from `os.environ`, and nothing in the codebase had ever actually loaded `workers/runtime/.env` — the README's `cp .env.example .env` step produced a file nothing read. Verified live, not just re-read: restarted the supervisor against the real local Postgres and a real (pre-existing, non-production) Highrise bot token — `bot_instances.status` for the affected instance went `stopped` → `provisioning` → `running`, with `instance_events` showing no `degraded`/`connect_timed_out` in between, confirming an actual Highrise session, not just a process that didn't crash.

Built entirely from data the page already had (no new detection logic); i18n'd across all 5 locales. Worth knowing: `error_kind` is populated almost exclusively as `token` today — `permissions`/`room` exist in the enum/copy but nothing writes them yet (`specs/04-bot-runtime.md`'s own long-standing open question) — so the copied blob will often just say "Needs attention" with no classified cause until that gap closes separately.

Verified end-to-end against the real local dashboard (not just `tsc`/`eslint`/JSON-validity, though those ran clean too): fetched the rendered instance page authenticated as two different real accounts — one with an empty event log, one with a populated one (the same instance this incident was diagnosed against) — confirming the button renders and no server/hydration error in either case. → `specs/04-bot-runtime.md`

## 2026-07-23 — Bug fix: dashboard boolean toggles silently defaulted to off for any never-explicitly-saved config key, breaking Avatar's Anchor spot on a live canary bot

Reported live against a real connected bot: the saved anchor spot was being ignored, bot spawning at the room's default entry point on every reconnect. `AvatarEngine.restore_position()` (`workers/runtime/catalog/avatar.py`) and the Python-side config gating were verified correct and already covered by passing integration tests against a real Postgres pool — the bug was entirely on the dashboard side.

Root cause: `schema-form.ts`'s `FieldSpec` never carried a leaf's JSON-Schema `default` through to the rendered field — only the separate `defaultsFromSchema` (used once, at instance-creation time) read it. `instance-config.tsx`'s `SectionCard`/`ConfigField` initialized every boolean toggle's checked state as `Boolean(config[key])`, which is `false` whenever the stored config is missing that key — not the field's actual schema default. Avatar's `position` section was merged into the schema on 2026-07-21, after Emote/Concierge/Warden; any instance whose `bot_instances.config` predates that merge (or simply never had its Avatar tab explicitly saved) had `config.position` entirely absent, so `position.enabled` (schema default `true`) rendered **unchecked**. Saving the config form for *any* reason — even something unrelated on another tab, since all modules' fields submit together — then persisted that visually-unchecked box as an explicit `enabled: false`, which both the in-game "anchor" command and the dashboard-set coordinate path check identically. From that point the bot silently never restored any saved position, in-game or dashboard-set, matching the report exactly.

**Fix:** `FieldSpec` now carries `default` (`schema-form.ts`); `SectionCard`'s `enabled`/gate state and `ConfigField`'s checkbox (`instance-config.tsx`, new `resolvedBoolean(value, fieldDefault)` helper) fall back to the field's schema default rather than `false` when the stored value is `undefined`. This is a general dashboard-rendering fix, not Avatar-specific — it protects every boolean toggle whose schema default is `true` against the same silent-flip-on-unrelated-save failure mode, including ones added to the schema after instances already exist.

**Not fixed by this change:** any instance whose config already has `position.enabled` explicitly persisted as `false` from before this fix stays that way — the rendering fix only stops it from happening to still-missing keys going forward. An owner already hit by this needs to open the instance's Avatar tab, re-check "Anchor spot" → "Enabled," and save once to clear it. → `specs/bots/avatar.md`, `apps/web/src/lib/schema-form.ts`, `apps/web/src/modules/instances/[id]/components/instance-config.tsx`

## 2026-07-23 — Dashboard-initiated ban/unban: owner can moderate from the app, no room presence needed for either party

Customer-facing question that turned into a real feature: can the room owner configure bans, ban/unban from the dashboard's existing Regulars card, and ban someone without personally being in the Highrise room? Spec'd and built same day (`specs/bots/moderation.md`'s "proposed" section, now "built"). Answer to all three: yes, with one real constraint — the *owner* never needs Highrise open, but the *bot* still has to be connected to the room, since `moderate_room` is WebSocket-only (no REST equivalent on `WebAPI`).

**New `moderation_requests` table** (`apps/web/src/db/schema.ts`, migration `0011_dizzy_punisher.sql`) is a work queue, not a log — `instance_events` is append-only and `warden_strikes` has decay-counter semantics, neither fits a one-off owner action the data plane needs to claim and mark done. Control plane only ever inserts a `pending` row and `NOTIFY`s; the supervisor/`WardenEngine` own every status transition after that (`pending` → `processing` → `applied`/`denied`/`failed`), same split as everything else in this architecture.

**Third Postgres NOTIFY channel**, `moderation.requested`, added alongside `config.updated`/`avatar_position.updated` (`apps/web/src/lib/notify.ts`'s `publishModerationRequested`; `supervisor.py`'s `_listen_config_updates` dispatch). `reconcile()` also sweeps pending requests for every running instance every tick (`_apply_pending_moderation_requests`, one batched claim query across all running instances — docs/cost-plan.md R4's posture, not one query per instance) — that sweep is the entire answer to "the owner clicked Ban while the instance was stopped": the row just waits and gets claimed the moment the instance is running again, no separate apply-on-connect path needed. `WardenEngine.apply_dashboard_action` (`workers/runtime/catalog/warden.py`) is the execution side: same throttle-acquire and `ResponseError` handling as the existing ladder/mod-command path, distinct `dashboard_moderation_applied`/`_denied` log shape so the activity feed can tell "the owner clicked this" apart from the automated ladder.

**Real, load-bearing discovery made while building the "ban by username" manual-entry path** (the user explicitly wanted this to work even for someone who's never visited the room): the SDK's own `webapi.get_users(username=...)` (`GET /users?username=...`, a collection/filter endpoint) is **dead against the live API** — 404s unconditionally, every query shape tried (confirmed with real `curl` against `webapi.highrise.game`, not just reasoned about). Both the `highrise` skill and `specs/bots/moderation.md` updated with this fact — it contradicts what the SDK models, so it's worth knowing before reaching for `get_users` anywhere else.

## 2026-07-23 — Bugfix: instance page crashed next-intl on every load — schema field docs run through `t.raw`, not `t`

User-reported: "nextjs console errors" on `/instances/[id]`. Root cause found by reproducing directly against the real dev server (minted a throwaway session via `psql`, curled the page, read `.next/dev/logs/next-development.log`) rather than guessing from source alone — the log showed `INVALID_MESSAGE: UNCLOSED_TAG` and `FORMATTING_ERROR` thrown by next-intl's real ICU parser on every load, not a one-off.

**Cause:** `app/[locale]/instances/[id]/page.tsx` resolved each schema field's title/description via `tSchema(path)` — next-intl's real translate call, full ICU parsing — whenever the key existed in the `schemaEmcee` messages namespace, which it does for essentially every field (`messages/*.json` mirrors the schema's own English copy 1:1 as the translation baseline). Several of those descriptions are bot-command/template-variable documentation containing literal `<...>`/`{...}` syntax that was never meant to be ICU markup — e.g. Emote's `"\"all <emote>\" makes everyone in the room perform it as a staggered wave."` or Concierge's `"Use {username}, {room_name}."` (describing template variables *available to the customer's own config*, not something to interpolate here). ICU reads `<emote>` as an unclosed rich-text tag and `{username}` as a required interpolation argument nothing supplies — both throw. `sectionsFromSchema()` (`lib/schema-form.ts`) was always given a lookup function; `fieldSpecFor`'s design (fall back to the schema's own English text when a message key is *missing*) anticipated this being an override mechanism, not the always-hit path it turned out to be in practice.

**Why nothing caught this sooner:** `schema-form.test.ts` calls `sectionsFromSchema(emceeSchemaV1)` with no `t` argument at all, so it only ever exercises the plain-schema-fallback branch — never the real-translation branch that actually breaks. The other call site (`instances/[id]/actions.ts`) also passes no `t`, for the same reason (it only needs field shape, not display copy). `page.tsx`'s render path was the sole place a real translator ever reached these strings.

**Fix:** one call site, `tSchema.raw(path)` instead of `tSchema(path)` — `t.raw()` returns the message value verbatim, no ICU parsing, which is what field documentation text needs (it's copy to display, not a template to fill in). Added a comment on `SchemaCopyLookup` (`lib/schema-form.ts`) spelling out why, so a future "simplify this" pass doesn't quietly revert it back to `t()`.

**Known gap, not closed here:** no unit test guards this specific regression — doing so would mean exercising a real next-intl translator (`use-intl`'s `createTranslator`) against the actual `schemaEmcee` messages, and `use-intl` isn't a declared dependency of this app (only pulled in transitively through `next-intl`), so wiring that in felt like more surface than this bugfix warranted. Caught and confirmed only by hitting the real dev server before/after — verified via `.next/dev/logs/next-development.log`: seven `ERROR`-level next-intl parse failures on every pre-fix load, zero after, HTTP 200 both times (next-intl was catching its own parse errors and continuing the render, not crashing the page outright — the errors were console-only, matching what was reported). `tsc --noEmit`, `eslint .`, and the full `vitest` suite (131, unchanged — this path has no direct test coverage either way) all clean. Test session row and rendered fixture files cleaned up after. → `apps/web/src/lib/schema-form.ts`

## 2026-07-22 — Redis dropped entirely: config pub/sub moved to Postgres LISTEN/NOTIFY

R6 from `docs/cost-plan.md`, done as a follow-up to the same day's cost pass (R2–R5, entry below): removed Redis from the app completely, not just the already-dead heartbeat writes (R2). The only thing Redis still did after R2 was carry two pub/sub channels — `config.updated` and `avatar_position.updated` — and pub/sub is a service Postgres can provide itself via `LISTEN`/`NOTIFY` with no new infrastructure, so there was no longer a reason to run a second stateful service anywhere this app is deployed.

**Sender side unchanged in shape, different transport.** `apps/web/src/lib/redis.ts` → new `src/lib/notify.ts`, same two exported functions (`publishConfigUpdated`, `publishAvatarPositionUpdated`), same best-effort contract (catch-and-log, never throw — "the loop makes it correct even if a notification drops" still holds, unchanged from the Redis version). Each now runs `select pg_notify('<channel>', $1)` through the existing pooled `db` client (drizzle's `sql` tag, so the payload is a bound parameter, not string-interpolated SQL) instead of publishing to a Redis client. `instances/[id]/actions.ts`'s one import site updated; no behavior change from the action's point of view.

**Receiver side needed a real design decision Redis's client library didn't.** `redis.asyncio`'s `pubsub().listen()` is an async generator — `_listen_config_updates` could just `async for message in pubsub.listen()`. asyncpg's `LISTEN`/`NOTIFY` support is callback-based (`Connection.add_listener(channel, callback)`), and critically, **LISTEN is session-scoped**: a connection returned to a pool gets its subscriptions silently dropped on release (asyncpg's own pool reset issues an implicit `UNLISTEN`). New `db.connect_for_listen()` opens one dedicated, never-pooled `asyncpg.Connection` per supervisor process, held for its whole lifetime — `Supervisor.__init__` now takes this as an explicit `listen_conn` parameter alongside the normal `pool`, and `main()` creates and closes it alongside the pool. Also had to choose between a sync or `async def` callback: asyncpg schedules each `async def` callback as its own independent task, which would let two notifications for the same instance apply out of order or concurrently — the sync-callback-plus-`asyncio.Queue`-plus-single-consumer-loop shape in `_listen_config_updates` was chosen specifically to preserve the old generator's strictly-one-at-a-time-in-arrival-order semantics, not because it's the simpler asyncpg pattern.

**Channel names carried over unchanged** (`config.updated`, `avatar_position.updated`, dots and all) — Postgres NOTIFY channel names are plain strings via `pg_notify()`, and asyncpg quotes the identifier for the `LISTEN` command internally, so the dot needed no renaming or escaping on either side.

**Fully removed, not just unused:** the `redis`/`redis.asyncio` packages from both `apps/web/package.json` and `workers/runtime/pyproject.toml` (confirmed uninstalled from both environments via `pnpm install` and `uv sync`, not just deleted from the manifest); the `redis` service from `docker-compose.yml` (torn down locally, confirmed via `docker compose up -d --remove-orphans`) and from both CI job's service containers; `REDIS_URL` from every `.env.example`. `apps/web/src/lib/rate-limit.ts`'s comment about a future Redis-backed limiter was updated to say Postgres instead, since that's the only shared-state store this app has left.

**Verified for real, cross-plane, not just via the existing mocked/pytest-level pubsub tests rewritten to call `pg_notify` instead of `redis.publish`** (which was also done — `test_config_hot_apply_via_postgres_notify`, `test_config_rejection_keeps_last_good`, plus a new `test_avatar_position_update_via_postgres_notify` closing a coverage gap where the avatar-position channel had only ever been proven via a direct handler call, never through the actual LISTEN dispatch). Beyond the pytest suite (183 Python tests, all passing with `redis` fully uninstalled from the venv), ran a standalone script that starts the real `Supervisor` against real Postgres with a real dedicated `asyncpg` LISTEN connection, connects a real bot through the existing fake-Highrise-server test double, then shells out to `pnpm exec tsx` to invoke the **actual, unmodified `apps/web/src/lib/notify.ts` module** (not a Python-side stand-in for it) for both channels — confirming the real control-plane code's `pg_notify()` call reaches the real data-plane code's `add_listener` callback, dispatches to the correct handler by channel name, and produces the expected `config_applied`/`avatar_position_applied` events, with a clean supervisor shutdown after. ## 2026-07-21 — Bot runtime: connect confirmation replaces optimistic "running" status
Customer-reported bug: started a bot with a correct room ID and token, got a success message, but the bot never appeared in the room — status kept showing "Live," the status log stayed empty, and a page refresh didn't change either. Root cause was the gap already flagged as an open question in `specs/04-bot-runtime.md`: the supervisor wrote `status = "running"` the instant it *started* a connect attempt, not once Highrise confirmed it. The official SDK's `bot_runner()` compounds this — it waits on the server's first WebSocket reply with no timeout at all, so a room the bot can never actually join (bad room id, missing designer rights — exact platform behavior here is one of the highrise skill's "known unknowns") can leave that call hanging forever instead of erroring. Since the supervisor's whole backoff/`disconnected`/`degraded` escalation only ran *after* `bot_runner()` returned, a hang meant nothing ever got logged and nothing ever downgraded the status — a silent, permanent false-positive.

Fix: `status` now goes to `provisioning` first (an enum value the dashboard already had UI copy for — "Starting…" — but the supervisor never used). `CatalogBot._confirm_connected()` (`workers/runtime/catalog/base.py`), called from `EmceeBot.on_start`, is the real "this attempt actually reached Highrise" signal — the earliest one the SDK exposes. The supervisor races that signal against the connect attempt with a `connect_confirm_timeout_s` (default 20s, `workers/runtime/supervisor.py`); a stuck attempt gets cancelled, logs a new `connect_timed_out` event (surfaced in the dashboard's status log same as `disconnected`/`degraded`), and counts toward the existing consecutive-failures → `degraded` escalation regardless of how long the timeout window was — a repeatedly-hanging instance still reaches `degraded` in a bounded number of attempts instead of staying "Live" forever. `error_kind` still can't distinguish *why* (bad room vs. missing designer rights vs. a one-off platform hiccup) — the SDK still doesn't surface that, only stdout prints — so that part of the spec's open question stands. → `specs/04-bot-runtime.md`

## 2026-07-21 — Control plane: React error boundaries, Sentry crash reporting, PostHog analytics

## 2026-07-21 — Crash-loop email alerts + a general operational status log

## 2026-07-20 — Loop/stop: EmoteBot's first post-v1 feature, off by default
Moved loop/stop out of `specs/bots/emote.md`'s "explicitly deferred" list and built it (`workers/runtime/catalog/emote.py`): `loop <emote>` repeats it for the speaker on an interval until `stop`, leaving the room, or a safety timeout; `stop` is a distinct word from emote-all's `stopall` (no collision) and only ever stops the caller's own loop, no permission check needed since it's inherently self-service.

Extended the shared config schema (`packages/schemas/emote/v1.json`) additively — a new `loop` section with `enabled` (**default false**, unlike the other three sections' default-true — this is explicitly the heaviest sustained-load feature per the spec's own words and isn't tuned against real limits, so it's opt-in), `interval_s`, `max_concurrent_loopers` (the spec explicitly called out needing this), `max_duration_s` (a safety auto-stop for a forgotten/orphaned loop, e.g. a disconnect that never fires a clean leave — whispers the user why when it fires), and `cooldown_s`. Purely additive (every new field optional with a default), so no schema version bump — same v1, still validates old stored configs unchanged. This is the first real test of "schema is the shared contract": the TS control plane's schema-driven form (`sectionsFromSchema`/`defaultsFromSchema`) picked up the new section with zero code changes, only test updates (the tests that assert the schema's *exact* section/default list, not the generic renderer itself).

Design decisions made explicit rather than left implicit: starting a new loop while already looping *switches* the emote (cancels old, starts new) rather than stacking a second loop or requiring `stop` first — and doesn't count against `max_concurrent_loopers` since it's not adding a looper. The switch-cleanup race (old task's `finally` running after a new task has already replaced it in `self._loops`) is handled with a compare-and-delete (`if self._loops.get(user_id) is task: pop(...)`) rather than an unconditional pop, which would otherwise sometimes delete the *new* task's dict entry. Blocked-by-cap attempts get a quiet whisper explaining why, unlike genuinely-unknown text which stays silent — this is a recognized command being capped, not gibberish, and silent failure on a paying customer's bot would read as broken. `on_user_leave` is now overridden (previously not) purely to cancel the leaver's own loop — emote-all still doesn't track roster via join/leave events, it snapshots fresh via `get_room_users()` at trigger time, cheaper and can't drift.

## 2026-07-20 — Python supervisor wired; lease-based claiming; verified via a protocol-compliant fake Highrise server
Built the real reconciliation loop (`workers/runtime/supervisor.py`): claim → spawn → heartbeat → hot-apply → stop, against real Postgres (`db.py`, plain asyncpg, no ORM) and real Redis (`heartbeat.py`). Resolved the shard-assignment open question in favor of the spec's own lean — lease-based claiming (`bot_instances.supervisor_id` + `lease_expires_at`, new migration `0002_add_lease_claiming`), atomic via `FOR UPDATE SKIP LOCKED`, so a crashed supervisor's instances get picked back up on the next claim cycle with no ops action. Tokens are decrypted fresh on every (re)connect attempt, not just once at spawn — that's what makes "replace token" take effect without a dedicated push signal.

No real Highrise bot token or room exists in this environment (Trust & Safety gated, no zero-registration bootstrap unlike Stripe's sandbox) — verification instead used a small fake WebSocket server (`tests/fake_highrise_server.py`) speaking the real wire protocol (`_type`-tagged JSON via cattrs, confirmed by reading `highrise/_unions.py` and `highrise/models.py` directly) against the **actual SDK's `bot_runner()`** via its `HR_BOTAPI_URL` env override, not a mock of our own code. Reading `highrise/__main__.py` also surfaced a genuinely useful fact: `bot_runner()` internally retries `ConnectionResetError`/`WSServerHandshakeError`/`TimeoutError` forever via its own throttler and only ever *returns* on a fatal `do_not_reconnect` application error — meaning the supervisor's own backoff/degraded escalation is correctly scoped to fatal credential/room-class failures, not network blips, which the SDK already absorbs invisibly. This directly shaped the design rather than being incidental — see the open-questions update in `specs/04-bot-runtime.md` on why precise `error_kind` classification isn't achievable yet (the SDK gives no structured reason for a fatal return, only stdout prints).

26 Python tests: DB-layer lease/claim semantics against real Postgres including a genuine two-pool concurrency test proving two supervisors never double-claim; five live tests driving the real `bot_runner()` against the fake server (connect → running status → heartbeat; desired_state flip → graceful stop; fatal token → degraded after N fast failures; config.updated hot-apply, both accepted and rejected); five unit-level edge cases (unknown catalog slug, multi-tick reconcile stability, shutdown draining, malformed/unrelated pub/sub payloads). Then ran `supervisor.py` itself as a real OS subprocess (not a pytest call) against the fake server: claimed a real instance, connected, wrote a real heartbeat, and on a real SIGTERM drained gracefully (lease released, heartbeat cleared, `status='stopped'`, event emitted, clean exit code) — proving the CLI entrypoint and signal handling, not just the orchestration logic.

Two real bugs found by the live tests, not caught by writing the code carefully the first time: (1) `self.running` was keyed by `row["id"]`, which asyncpg returns as `uuid.UUID`, while the Redis pub/sub payload's `instanceId` is always a JSON string — every hot-apply lookup would have silently no-op'd in production. Fixed by normalizing to `str()` at the one place instance ids enter the supervisor's own state. (2) `highrise.__main__` imports `pkg_resources` at module load without declaring `setuptools` as a runtime dependency, and modern `setuptools` no longer bundles it — pinned `setuptools<81`, logged as a real fragility in `specs/04-bot-runtime.md` since that pin may not stay satisfiable indefinitely.

Known gap: nothing here has touched the actual Highrise platform — no real rate limits, error message shapes, or protocol quirks are confirmed. That's explicitly deferred to a canary instance once real bot credentials exist, matching the spec's own "measure real platform limits" posture. → `specs/04-bot-runtime.md`

## 2026-07-20 — Instance creation flow: paste-token → seal → config form → Redis wake
End-to-end BotInstance lifecycle from the dashboard: `/instances/new` picks a catalog bot from the real `catalog_bots` table (only `emote` today), takes a room ID or share link (normalized — last path segment if a URL was pasted) and a token, seals it via `sealToken()`, and inserts with `config` set to the schema's own declared defaults. `desiredState`/`status` are left at their DB defaults (`stopped`/`created`) — creation never flips them, since only billing may (`specs/02-architecture.md`); the instance page says so plainly ("awaiting checkout") rather than pretending the bot is live.

`/instances/[id]` renders a config form **generated from the JSON Schema**, the architecture spec's core leverage claim, now real: `sectionsFromSchema`/`defaultsFromSchema`/`parseConfigFormData` (`src/lib/schema-form.ts`) walk the schema's fixed two-level shape (object of sections → primitive leaves) rather than a fully general recursive JSON Schema walker — extend when a bot config actually needs deeper nesting. Save path is exactly the spec's words: validate (`ajv`, `src/lib/schema-validate.ts`) → write Postgres → publish `config.updated` on Redis (payload carries only the instance id — Postgres stays sole source of truth, publish failures are swallowed since "the loop makes it correct even if pub/sub drops," `specs/04-bot-runtime.md`). Token replace reuses `sealToken()` and never puts a token value in `instance_events`.

Two bugs the build/tests didn't catch, found only by driving the real flow end-to-end:
- `sealToken()`'s catch-all conflated "bad token format" with "server misconfigured" (e.g. `TOKEN_SEAL_PUBLIC_KEY` unset) into the same misleading "that token doesn't look right" message. Split into a distinguished `TokenFormatError`; anything else now surfaces as a real error instead of blaming the user for our config.
- The config form's `<input type="number" min max>` means real users can never submit an out-of-range value — the browser blocks it before JS or the server sees it. Server-side rejection of the same value is still covered (`schema-validate.test.ts` against the live schema), but that's now known to be a defense-in-depth backstop against a hostile client, not a path a real user can hit through the UI.

Verified with a real headless-Chromium run (Playwright driving system Chrome, not a mock) against live Postgres + Redis: full click-through — sign in, attest age, create instance, view schema-rendered defaults, save a config change, replace the token — then confirmed independently: the Redis subscriber actually received `config.updated`; Postgres held the submitted config verbatim; **a second signed-in user hitting the first user's `/instances/[id]` got a 404**, proving `getOwnedInstance`'s tenant scoping; and the replaced token's stored ciphertext was decrypted through the real `tokenbox.py` (separate process, separate keypair half) to the exact replacement value — the strongest possible proof the two-plane token design (`fd10d1a`) holds under a real write, not just the original cross-plane script's synthetic round trip.
