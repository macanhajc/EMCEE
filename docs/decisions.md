## 2026-07-21 — Dashboard start/stop switch: a subscription entitles, it no longer runs the bot
Amends the billing principle "billing state drives entitlement, never the reverse" (`specs/03-billing.md`): it was true in the strict sense but had the practical effect of billing *also* deciding "running," since `desired_state` was flipped straight to `"running"` the moment a purchase or an entitled Stripe status landed. A new `bot_instances.user_enabled` boolean (default `false`, migration `0007_add_user_enabled`) splits that back into two independent gates — `desired_state = entitled && user_enabled` (`resolveDesiredState()`, `apps/web/src/lib/billing-state.ts`) — so a fresh checkout, a trial converting, or a `past_due` recovering all still leave the bot off until the customer presses **Start**. New instances already defaulted to `desired_state = "stopped"` at creation (unchanged); this closes the other gap, the post-payment one.

**Both writers of `desired_state` now gate through the same function.** The Stripe webhook (`onSubscriptionChanged`) computes entitlement via `mapSubscriptionStatus` same as before, then ANDs it with the instance's current `user_enabled` before writing — `onCheckoutCompleted` no longer touches `desired_state` at all, since a fresh purchase is exactly the case that must *not* auto-start. The new dashboard action (`setBotRunning`, `apps/web/src/app/instances/[id]/actions.ts`) requires an entitled subscription to exist at all (reusing `getActiveSubscriptionForInstance`'s existing trialing/active/past_due filter, so entitlement is true by construction whenever the action is reachable) and writes `user_enabled` + the resulting `desired_state` together. Neither writer can start the bot alone.

**No new Redis channel.** Checked `workers/runtime/supervisor.py` before wiring anything: `config.updated` only hot-applies config to an *already-running* bot (looked up in `self.running`), and there's no existing "stop now" channel either — both start and stop, including the pre-existing billing-driven flips, rely entirely on the ~10s reconcile-loop poll. Publishing on the new action would have been a no-op dressed up as a feature; left it alone, same latency contract as billing flips already have.

**UI:** a Start/Stop button was added to the subscription-info card on the instance page (`apps/web/src/app/instances/[id]/page.tsx`), visible only once a subscription exists — matching the existing "Subscribe to activate" vs. "Manage billing" branch there. Backfill in the migration sets `user_enabled = true` for any row already `desired_state = "running"`, so no already-live instance goes dark the next time a billing event recomputes it (moot in the current dev DB — both existing instances are `stopped` — but correct in general).

Updated `specs/02-architecture.md` and `specs/03-billing.md` (principle #2 and the state-machine section) to describe entitlement and running as two separate things. Verified: `tsc --noEmit`, `eslint`, full `vitest` suite (104, +4 new `resolveDesiredState` cases) against real local Postgres; migration applied and confirmed column + backfill on the real dev DB; screenshotted both button states (Start on an unstarted-but-subscribed instance, Stop after clicking it) in a real browser via a headless-Chromium session. → `specs/02-architecture.md`, `specs/03-billing.md`

## 2026-07-21 — Avatar's anchor spot also settable from the dashboard, not just in-game
Fast-follow on the same day Avatar shipped: the "Anchor spot" card on the instance page now has a second, independent way to set the bot's saved position — raw x/y/z/facing number inputs, pre-filled from whatever's already saved, alongside the existing in-game "say anchor" flow. For an owner who already knows the coordinates (from a prior anchor, or another tool) this beats walking into the room to re-trigger it.

**Coordinates still don't live in config.** The draft spec's "no coordinates ever live in config" stance (avoiding a second source of truth alongside `avatar_positions`) holds — the dashboard form writes straight to `avatar_positions` via a new `apps/web/src/db/avatar-positions.ts` helper, the same table + row the in-game command already writes to, not `bot_instances.config`.

**A second Redis channel, not a reuse of `config.updated`.** `apply_config` only swaps `bot.config` in memory; it was never wired to re-read `avatar_positions`, so a config-update signal wouldn't have made a dashboard-set position take effect live. Added `avatar_position.updated` (published by `publishAvatarPositionUpdated`, `apps/web/src/lib/redis.ts`) as its own channel, handled by a new `Supervisor._handle_avatar_position_update` mirroring `_handle_config_update`'s shape (parse payload, look up the running instance, no-op if not ours), which calls a new `EmceeBot.apply_avatar_position()` → `AvatarEngine.restore_position()` (renamed from the private `_restore_position`, now also the `on_start` entry point) to re-teleport off the freshly-saved row. No reconnect needed.

**Form nesting, worked around with the HTML `form=` attribute.** The instance page's Configuration section is one shared `<form>` across every module (all of it must stay mounted so a save doesn't wipe other modules' fields — see the standing comment in `instance-config.tsx`). The position editor can't be a nested `<form>` inside that one, and pulling the "Anchor spot" section's own schema-driven fields (`enabled`/`permission`/`allowlist`) out of the shared form to make room would silently drop them from every other module's save. Resolved with the standard (if less common) `form="avatar-position-form"` attribute on the new inputs/button: they render inside the same visual card as the schema-driven fields but submit to an independent `<form id="avatar-position-form">` rendered as a sibling, not a descendant, of the config form — valid HTML, no nesting.

Verified: `tsc --noEmit`, `eslint`, and the full `vitest`/`pytest` suites (89 web, 181 runtime — 6 new: `apply_avatar_position` teleporting to a freshly-saved and then a re-saved spot, no-op while `position.enabled` is off, and the supervisor-side wiring/malformed-payload/unrelated-instance cases) all green against real local Postgres/Redis. Not checked in an actual browser — no interactive browser tool available this session. → `specs/bots/avatar.md`

## 2026-07-21 — Avatar ships; SDK-reading pass resolves the outfit module's load-bearing unknown
Avatar (`specs/bots/avatar.md`) moves from "draft roadmap, not yet scoped to SDK capability" to shipped in full — all four brainstormed pieces (anchor spot, idle emote loop, reaction-back, outfit) landed together as the fourth module composed into Emcee (`workers/runtime/catalog/avatar.py`'s `AvatarEngine`, wired into `EmceeBot` in `emcee.py`), rather than splitting outfit off as a blocked fast-follow like the draft spec's own open questions anticipated.

**The blocking unknown resolved before any code was written.** The draft flagged "is changing the bot's own outfit even exposed by the SDK, or only settable at bot-account creation" as the whole module's load-bearing question. Reading the pinned SDK source directly (`highrise-bot-sdk` 25.1.0 — `models.py`, `webapi.py`, `models_webapi.py`, not just the docs) confirmed `set_outfit`/`get_my_outfit`/`get_user_outfit`/`get_inventory` all exist and work at runtime, including a live read of *another* user's outfit — both open questions resolved to "yes," clearing the path to build outfit alongside presence & flair instead of after it.

**The real constraint that replaced it.** `set_outfit` replaces the whole outfit, and Highrise's own server enforces required-slot completeness (one item each from body/eye/eyebrow/nose/mouth plus a lower-body combo) — an incomplete list is rejected outright. This module never reimplements that rule itself; a rejection just keeps the bot's previous outfit, same "keep last-good" posture `CatalogBot.apply_config` already uses. Default outfit and named presets lean on the owner supplying a complete item id list; "copy \<username\>" (clone) can't make that assumption — a stranger's outfit intersected with the bot's own inventory is rarely complete on its own — so it merges matched items onto the bot's *current* outfit by category instead of replacing wholesale (`_merge_by_category`, one `self.webapi.get_item()` call per candidate item to learn its category, since category lives only on the webapi's fuller `Item`, not the outfit/inventory one). `min_match` (default 2) skips the swap entirely with a whisper rather than applying a near-empty result that reads as broken.

**Anchor spot sidesteps an unconfirmed event rather than depending on it.** There's no confirmed SDK event for "this bot's own avatar was moved by someone else," so "owner drags the bot into place" wasn't buildable as originally imagined. Instead, saying "anchor" teleports the bot to the *speaker's* last-known floor position (tracked via the already-confirmed `on_user_join`/`on_user_move`) and persists it (`avatar_positions`, one row per instance, restored on every `on_start`) — gets the same product outcome without the unknown.

**Presets encoded as lines, not objects, to avoid a generator change.** `outfit_presets.presets` is a `string[]` of `"name: id1, id2, ..."` lines rather than an array of `{name, item_ids}` objects — deliberately, so the dashboard's existing two-level schema-form generator (`apps/web/src/lib/schema-form.ts`) needed zero changes, same call Concierge's spec made when it dropped VIP tiers rather than extend that generator speculatively (2026-07-20 entry below).

**No auto-buying.** `buy_item`/`tip_user` both exist and both spend the bot's own Gold-denominated Highrise wallet — excluded from this module entirely as a documented stance (`CLAUDE.md`'s Gold constraint), not a silent judgment call buried in code.

Verified with 34 new unit tests against `FakeHighrise`/`FakeWebAPI` (both extended with outfit/inventory/position/reaction fakes) covering every sub-feature, permission gating (owner/owner_designers/allowlist, same shape as Emote's `all <emote>` and Warden's exemptions), the seated-vs-standing anchor edge case, idle-loop config hot-toggle, clone's category-merge behavior and `min_match` guard, and cross-instance position persistence against real Postgres (`avatar_positions`, migration `0006_add_avatar_positions`). 171 Python tests total, all passing. Dashboard side needed no source changes — `schema-form.ts` already handled every leaf shape the new sections use — only its tests grew to cover the six new `x-module: "avatar"` sections; 89 web tests passing.

Known gap, same shape as every other module before its own canary pass: nothing here has touched the real platform, so required-slot completeness behavior, exact rejection shapes, and real reaction/emote timing are confirmed only against docs and test doubles. → `specs/bots/avatar.md`

## 2026-07-21 — Warden ships as a trimmed v1; SDK spike resolves the moderation-primitives open question
Warden (`specs/bots/moderation.md`) moves from "deferred, post-v1 candidate" to shipped, as the third module composed into Emcee alongside Emote and Concierge — same `EngineClass(bot)` pattern (`workers/runtime/catalog/warden.py`'s `WardenEngine`, wired into `EmceeBot` in `emcee.py`).

**Scope: trimmed core, not the full draft.** Filter (custom terms only), anti-spam (rate + duplicate), strike ladder, action log, and in-chat mod commands (`!warn`/`!mute`/`!kick`) are built. Raid guard, curated base blocklists (harassment/links/solicitation, PT-BR), and caps/emoji-flood heuristics are deferred, not built — same trim-to-buildable call as Concierge's v1 dropping VIP tiers and presence/flair (2026-07-20 entry below). Raid guard in particular was already self-flagged in the original draft as mitigation-only (no real join-gating in the bot API), so cutting it isn't a regression against what it could ever have promised.

**SDK spike, before any code was written.** The draft spec's open question — "can a designer-rights bot ban, or only kick/mute? does ban support a duration? is there an unban API?" — was answered by reading the pinned SDK source directly (`highrise-bot-sdk` 25.1.0, `workers/runtime/.venv/lib/python3.11/site-packages/highrise/`) rather than guessing from docs. Findings: `moderate_room(user_id, action, action_length)` looks fire-and-forget but actually awaits the server's ack and raises `ResponseError` on failure — so the privilege question doesn't need a static answer at all, the code just needs to catch the failure, which `WardenEngine._apply_action` does (logs a `moderation_denied` event, whispers the mod-command requester if there was one, never crashes the handler). Ban supports a duration, same as mute — the draft's "ban is permanent" assumption was wrong, corrected in the spec. There's no "unmute" action and no "list currently muted/banned" read API, confirming Warden's own persisted strike state is the only source of truth for "who's under what," not something queryable from the platform. `on_moderate` fires for every moderation event in the room (ours or a human moderator's own in-client action) — comparing `moderator_id` against `self.bot.highrise.my_id` is what lets external mod actions get logged to the activity feed without also striking on top of them.

**Schema: flat and gate-based, not the draft's `ladder.rungs` array.** The draft sketched the strike ladder as an array of `{strikes, action, duration_m}` objects. `apps/web/src/lib/schema-form.ts`'s generator only understands a flat two-level shape (object of primitive-leaf sections) — the same wall Concierge hit with per-entry VIP tiers. Resolved the same way: fixed named fields (`ladder.mute_at_strikes`/`kick_at_strikes`/`ban_at_strikes`) instead of a dynamic array, using the schema's existing `x-enabled-by` gate (built for Concierge's quiet-hours fields) to keep the ban rung off by default without a separate UI mechanism. Zero changes needed to the schema-form generator or `instance-config.tsx`'s renderer — `filter`/`anti_spam`/`ladder`/`exemptions`/`commands` sections just landed in `packages/schemas/emcee/v1.json` tagged `x-module: "warden"`, and a `{ key: "warden", label: "Warden" }` entry in `LIVE_MODULES` turned on the dashboard tab. The security floors from `05-security.md` ("ban always requires ≥2 strikes," "max mute 24h") are schema-level constraints (`ban_at_strikes minimum: 2`, `mute_duration_s maximum: 86400`), enforced by both ajv on save and `jsonschema` on the runtime side — the same defense-in-depth path every other module's config already goes through, nothing new to build.

**Strike persistence: `warden_strikes`, same shape as `greeter_visits`.** New table (`apps/web/drizzle/0005_add_warden_strikes.sql`), composite PK `(bot_instance_id, user_id)`. `db.bump_strikes` (`workers/runtime/db.py`) mirrors `record_visit`'s single-round-trip upsert but computes decay at write time — a stale `last_strike_at` (older than `strike_decay_h`) resets the count to 1 instead of incrementing it, so no cron job is needed for decay. `WardenEngine` falls back to an in-memory per-process counter when `db_pool` is `None`, same degrade-not-silence pattern as `GreeterEngine._visits`.

**Action log: first real consumer of `instance_events`'s `moderation` kind.** The column comment already anticipated this (`kind: "moderation" | ...`); Warden is the first module to actually call `db.insert_event` with it — every filter hit, strike, mute/kick/ban attempt (applied or denied), and external moderation event gets a row. `apps/web/src/db/warden-events.ts`'s `getRecentModerationEvents` + `activity-log.tsx`'s `ActivityLog` render the most recent 20 on the instance page, same placement pattern as Concierge's `RegularsTable`. No filter-by-user/action UI in trimmed v1 — the draft's fuller "90-day retention, filterable" ambition, cut the same way raid guard was.

**Verified:** full `workers/runtime` pytest suite (137 tests, including 29 new `test_warden_bot.py` cases covering filter word-boundary/squash matching, ladder priority ordering, exemptions, mod commands, `ResponseError` handling, external-moderation double-punish avoidance, and strike decay) and the web app's typecheck/lint/vitest suite (88 tests, `schema-form.test.ts` extended for the new sections) all green against the real local Postgres/Redis. Not yet verified against a live Highrise room — `moderate_room`'s actual permission behavior and duration units remain empirically unconfirmed until then. → `specs/bots/moderation.md`

## 2026-07-20 — Concierge visit-stats persistence: `greeter_visits` table, generic `db_pool` capability on every catalog bot
Fourth pass on Concierge the same day. Visit counts were in-memory-per-process since the original build — every reconnect or redeploy reset `{visit_count}` and farewell's `min_visits` to zero, an explicitly flagged known gap rather than an oversight. Closed it.

New table `greeter_visits` (`apps/web/src/db/schema.ts`, migration `0004_add_greeter_visits.sql`, real `drizzle-kit generate` diff this time — not a hand-written custom migration like the emote→emcee rename, since this is an actual DDL change): `(bot_instance_id, user_id)` composite PK, `visit_count`, `first_seen_at`/`last_seen_at`, cascade-deletes with the instance. `user_id` is the Highrise user id, not one of ours. `workers/runtime/db.py`'s `record_visit` does the whole increment as one atomic `INSERT ... ON CONFLICT (bot_instance_id, user_id) DO UPDATE SET visit_count = greeter_visits.visit_count + 1 ... RETURNING visit_count` — no read-then-write race between concurrent joins.

Wiring choice: rather than threading a `pool`/`instance_id` constructor argument through `CatalogBot` and every subclass (forcing every future module to accept parameters only one module today needs), `CatalogBot.__init__` now initializes `self.db_pool`/`self.bot_instance_id` to `None`, and `supervisor.py`'s `_spawn_instance` sets both as plain attributes right after constructing the bot — a generic capability every catalog bot gets for free, matching `specs/04-bot-runtime.md`'s already-stated policy ("catalog bots may only reach Highrise and our own Postgres/Redis"), not a Concierge-specific wire-up. `GreeterEngine._record_visit` uses it when present, and falls back to the pre-existing in-memory `_visits` dict when it isn't (unset in standalone/unit-test construction) or when a write raises — a DB hiccup degrades to an uncounted-but-still-sent greeting, deliberately not silence: the outer handler-shielding wrapper would otherwise turn any exception here into no greeting at all for that join. `_visits` itself is repurposed as a same-session cache of the latest known count (refreshed every join) so farewell's `min_visits` check never needs a second query to re-read what the join handler already just learned.

Verified against real Postgres, not mocked: `test_db.py` gained three tests for `record_visit` (increments correctly, independent per instance × user, username updates on revisit — the dashboard "regulars" table this feeds isn't built yet, but the data is real and queryable). `test_greeter_bot.py` gained two integration-level tests — one constructs two separate `EmceeBot` objects backed by the same real `bot_instance_id` and confirms the second correctly reads "visit #2" from what the first wrote (proving actual cross-restart survival, not just that the SQL is well-formed), and one wires a pool whose `.acquire()` raises and confirms the greeting still sends with a session-local count instead of going silent. All 25 pre-existing Concierge tests (the in-memory fallback path) still pass unchanged, since none of them set `db_pool`. → `specs/bots/greeter.md`

## 2026-07-20 — Emcee merge: Concierge folded into one bot/instance/token with Emote; control plane wired end-to-end
Third pass on Concierge the same day (brainstorm → build → this). Asked to wire Concierge into the control plane the way Emote already was — seed it into `catalog_bots`, hook up the dashboard — and the naive version of that broke the product's own stated model. Every spec (`emote.md`, `greeter.md`, `avatar.md`) says feature modules share one bot/instance/token; the code had `EmoteBot` and `GreeterBot` as two independent `CatalogBot` subclasses with their own slugs. Seeding `greeter` as a second `catalog_bots` row would have made `/instances/new`'s `bots[0]` pick nondeterministic (real regression risk to the live Emote purchase flow) and, more fundamentally, made Concierge a *second separately-purchasable bot* — its own token, its own room — not a module of the one a customer already has.

Chosen fix, picked over two cheaper alternatives (a real bot-picker UI accepting the two-separate-products model; or seeding the row without exposing it anywhere yet) after asking: **merge the runtime**, matching what the specs already promised.

**Python (`workers/runtime/catalog/`):** `EmoteBot`/`GreeterBot` demoted from `CatalogBot` subclasses to plain `EmoteEngine`/`GreeterEngine` classes that read/write through an owning bot (`self.bot.highrise`/`.throttle`/`.config`/`._room_owner_id`). New `emcee.py`'s `EmceeBot(CatalogBot)`, `SLUG = "emcee"`, composes both engines behind one connection/throttle/config and is the only thing whose handlers `CatalogBot.__init_subclass__`'s shielding actually wraps — each handler just dispatches into the relevant engine(s), `on_user_leave` into both (Emote cancels the leaver's loop, Concierge logs a farewell). Supervisor's `CATALOG` now has one entry, `{"emcee": EmceeBot}`. Existing tests (`test_emote_bot.py`, `test_greeter_bot.py`) construct `EmceeBot` and reach into `bot._emote.*`/`bot._greeter.*` for internals that used to be direct attributes — mechanical, not rewritten.

**Schema:** `emote/v1.json` + `greeter/v1.json` merged into one `packages/schemas/emcee/v1.json`, all 7 sections flat (no schema-level module boundary), each tagged `"x-module": "emote"` or `"concierge"` — a vendor-extension keyword the dashboard reads for tab grouping, meaningless to validation. Ajv's strict mode rejects unrecognized keywords by default (`"strict mode: unknown keyword: x-module"`, caught by the web test suite immediately) — registered via `ajv.addVocabulary(["x-module"])` rather than disabling `strict` wholesale, which would've also relaxed real correctness checks. Python's `jsonschema` never had this problem — unrecognized keywords are spec-legal and silently ignored, no strict mode to fight.

**Second real gap the merge surfaced, not introduced by it:** Concierge's schema needed bare `type: "string"` leaves (`vip.template`, `quiet_hours_start/end/tz`, `farewell.public_template`) that `schema-form.ts`'s `fieldSpecFor` had never supported — it only recognized enum/boolean/integer/array, silently returning `null` (and dropping the field entirely, comment and all: *"extend when a bot needs one"*) for anything else. Left alone, saving *any* config change on Concierge would have submitted a form missing those fields' inputs entirely, silently blanking them in storage on every save — not a hypothetical, a guaranteed data-loss bug on the very first save. Added a `"string"` `FieldSpec` kind end to end: `fieldSpecFor`, `parseConfigFormData`, and a plain text `<Input>` in `instance-config.tsx`.

**Dashboard tabs:** `InstanceConfig` already had a `BOT_ROADMAP`-driven tab bar with disabled "coming soon" placeholders — Concierge just needed to become a live one. The trap here: Radix's `TabsContent` unmounts inactive panels by default, so putting each module's `SectionCard`s inside real `TabsContent` blocks would mean submitting the form while on the Emotes tab silently drops every Concierge field from the `FormData` (and vice versa) — wiping the other module's saved config on every save. Fixed by keeping one shared `<form>` outside any `TabsContent`, with module visibility toggled by a plain Tailwind `hidden` class off local `activeModule` state — same "hidden, not unmounted" idiom `SectionCard` already used one level down for its own enabled-toggle sub-fields. Radix `Tabs`/`TabsList`/`TabsTrigger` still drive the tab-button UI/UX; only the content-mounting semantics were avoided. `BOT_ROADMAP` lost its `Concierge` entry (real tab now); `roadmap.ts`, `how-it-works.tsx`, and the hero mockup caption updated for accuracy.

**Data migration, not just seed:** the existing local dev DB had real `bot_instances` rows on `catalog_bot_slug = 'emote'` — a rename needed an actual migration (`drizzle/0003_rename_emote_to_emcee.sql`), not just changing what `seed.ts` inserts going forward. Order matters under the FK: insert the `emcee` row (additive), repoint `bot_instances` to it, drop the `emote` row — satisfies the FK at every intermediate step, not just the end. `ON CONFLICT DO UPDATE` rather than `DO NOTHING` on the insert, because the Python test suite's `conftest.py` fixture inserts a bare-bones `catalog_bots` placeholder against this same shared dev DB on every run (did the same for `emote` before this rename) — `DO NOTHING` would've left that placeholder's null tagline/price-ids in place over the real data. `STRIPE_EMOTE_*_PRICE_ID` env vars renamed to `STRIPE_EMCEE_*` (`.env` + `.env.example`) — same underlying Stripe objects, the real product was already named "Emcee (Emote Bot)" in the sandbox, this just stopped the env var name from lying about it.

Verified for real, not just by reasoning about it: ran the actual migration against the live local Postgres (`docker exec` before/after queries confirmed the row rename and both existing instances' `catalog_bot_slug` flip); re-ran `seed.ts` and confirmed idempotency; full suites green (98 Python, 87 web, `tsc --noEmit` clean, `eslint` clean); then — since no browser-automation tool was available this turn — inserted a real session row directly into Postgres, hit `/dashboard`, `/instances/new`, and a real `/instances/[id]` through the actual running dev server with `curl` and that session cookie, and confirmed the rendered HTML: correct Emcee tagline, `BOT_ROADMAP` no longer lists Concierge, and the config page's real form field names (`welcome.enabled`, `vip.template`, `vip.users`, `farewell.min_visits`, `quiet_hours_tz`) plus both `Emotes` and `Concierge` tab labels are actually present in server output. Didn't click through in an actual browser (no tool for it this turn) — SSR output and the field-level round-trip is proven, live client-side tab-switching interaction isn't. Test artifacts (session, user, instance) cleaned up after. → `specs/bots/emote.md`, `specs/bots/greeter.md`, `specs/04-bot-runtime.md`

## 2026-07-20 — Loop/stop: EmoteBot's first post-v1 feature, off by default
Moved loop/stop out of `specs/bots/emote.md`'s "explicitly deferred" list and built it (`workers/runtime/catalog/emote.py`): `loop <emote>` repeats it for the speaker on an interval until `stop`, leaving the room, or a safety timeout; `stop` is a distinct word from emote-all's `stopall` (no collision) and only ever stops the caller's own loop, no permission check needed since it's inherently self-service.

Extended the shared config schema (`packages/schemas/emote/v1.json`) additively — a new `loop` section with `enabled` (**default false**, unlike the other three sections' default-true — this is explicitly the heaviest sustained-load feature per the spec's own words and isn't tuned against real limits, so it's opt-in), `interval_s`, `max_concurrent_loopers` (the spec explicitly called out needing this), `max_duration_s` (a safety auto-stop for a forgotten/orphaned loop, e.g. a disconnect that never fires a clean leave — whispers the user why when it fires), and `cooldown_s`. Purely additive (every new field optional with a default), so no schema version bump — same v1, still validates old stored configs unchanged. This is the first real test of "schema is the shared contract": the TS control plane's schema-driven form (`sectionsFromSchema`/`defaultsFromSchema`) picked up the new section with zero code changes, only test updates (the tests that assert the schema's *exact* section/default list, not the generic renderer itself).

Design decisions made explicit rather than left implicit: starting a new loop while already looping *switches* the emote (cancels old, starts new) rather than stacking a second loop or requiring `stop` first — and doesn't count against `max_concurrent_loopers` since it's not adding a looper. The switch-cleanup race (old task's `finally` running after a new task has already replaced it in `self._loops`) is handled with a compare-and-delete (`if self._loops.get(user_id) is task: pop(...)`) rather than an unconditional pop, which would otherwise sometimes delete the *new* task's dict entry. Blocked-by-cap attempts get a quiet whisper explaining why, unlike genuinely-unknown text which stays silent — this is a recognized command being capped, not gibberish, and silent failure on a paying customer's bot would read as broken. `on_user_leave` is now overridden (previously not) purely to cancel the leaver's own loop — emote-all still doesn't track roster via join/leave events, it snapshots fresh via `get_room_users()` at trigger time, cheaper and can't drift.

Verified with 13 new unit tests against the same `FakeHighrise` pattern (start/repeat, unknown emote, stop scoping to the caller only, start-cooldown, emote-switching including the cleanup race, cap enforcement and its whisper, cap *not* blocking an existing looper's switch, natural auto-stop via `max_duration_s` with its whisper, `on_user_leave` cancellation). One test bug caught during the first run, not a code bug: asserting on `self._loops[user_id]` *after* stopping a loop 404s, because the loop's own cleanup already removed it by then — fixed by capturing the task reference before cancelling, which is itself a small confirmation that the cleanup-on-stop design works as intended.

Verified against the live sandbox, not mocks: a real Playwright-driven purchase through Stripe's actual hosted test checkout (card 4242...4242) — Stripe's own UI showed "Start trial" confirming the trial wired correctly, and the resulting real Subscription object confirmed `trial_end - trial_start` = exactly 604800s, correct BRL price, correct metadata. Since the MCP tool doesn't expose the Events API either, fetched the real event payloads directly via the `stripe` SDK with the same key and replayed them (self-signed with a local-only webhook secret, `Stripe.webhooks.generateTestHeaderString`) against the actually-running local webhook endpoint: correct processing, correct idempotent no-op on replay, correct 400 on a tampered signature. Resulting DB state confirmed row-by-row: `subscriptions` mirror correct, `bot_instances.desired_state` → `running` while `status` stayed untouched, `users.stripeCustomerId` captured, `instance_events` audit trail complete with zero sensitive data, `trial_registry` populated. The Customer Portal button was confirmed to reach a real `billing.stripe.com` session.

Known gap, logged in `specs/03-billing.md`: no live webhook endpoint is registered anywhere (needs a public URL), so Stripe's actual delivery/retry behavior is unexercised — today's proof is that the handler is correct given a real event, not that Stripe can reach it yet. Pix also isn't enabled on this sandbox (test-account default), so Pix-specific behavior remains an open verification item for the real BR account. → `specs/03-billing.md`

## 2026-07-20 — Instance creation flow: paste-token → seal → config form → Redis wake
End-to-end BotInstance lifecycle from the dashboard: `/instances/new` picks a catalog bot from the real `catalog_bots` table (only `emote` today), takes a room ID or share link (normalized — last path segment if a URL was pasted) and a token, seals it via `sealToken()`, and inserts with `config` set to the schema's own declared defaults. `desiredState`/`status` are left at their DB defaults (`stopped`/`created`) — creation never flips them, since only billing may (`specs/02-architecture.md`); the instance page says so plainly ("awaiting checkout") rather than pretending the bot is live.

`/instances/[id]` renders a config form **generated from the JSON Schema**, the architecture spec's core leverage claim, now real: `sectionsFromSchema`/`defaultsFromSchema`/`parseConfigFormData` (`src/lib/schema-form.ts`) walk the schema's fixed two-level shape (object of sections → primitive leaves) rather than a fully general recursive JSON Schema walker — extend when a bot config actually needs deeper nesting. Save path is exactly the spec's words: validate (`ajv`, `src/lib/schema-validate.ts`) → write Postgres → publish `config.updated` on Redis (payload carries only the instance id — Postgres stays sole source of truth, publish failures are swallowed since "the loop makes it correct even if pub/sub drops," `specs/04-bot-runtime.md`). Token replace reuses `sealToken()` and never puts a token value in `instance_events`.

Two bugs the build/tests didn't catch, found only by driving the real flow end-to-end:
- `sealToken()`'s catch-all conflated "bad token format" with "server misconfigured" (e.g. `TOKEN_SEAL_PUBLIC_KEY` unset) into the same misleading "that token doesn't look right" message. Split into a distinguished `TokenFormatError`; anything else now surfaces as a real error instead of blaming the user for our config.
- The config form's `<input type="number" min max>` means real users can never submit an out-of-range value — the browser blocks it before JS or the server sees it. Server-side rejection of the same value is still covered (`schema-validate.test.ts` against the live schema), but that's now known to be a defense-in-depth backstop against a hostile client, not a path a real user can hit through the UI.

Verified with a real headless-Chromium run (Playwright driving system Chrome, not a mock) against live Postgres + Redis: full click-through — sign in, attest age, create instance, view schema-rendered defaults, save a config change, replace the token — then confirmed independently: the Redis subscriber actually received `config.updated`; Postgres held the submitted config verbatim; **a second signed-in user hitting the first user's `/instances/[id]` got a 404**, proving `getOwnedInstance`'s tenant scoping; and the replaced token's stored ciphertext was decrypted through the real `tokenbox.py` (separate process, separate keypair half) to the exact replacement value — the strongest possible proof the two-plane token design (`fd10d1a`) holds under a real write, not just the original cross-plane script's synthetic round trip.

## 2026-07-20 — Auth: Auth.js wired — Google OAuth + magic link, Node-runtime route gating
Auth.js v5 (beta) on the Drizzle adapter, against the auth tables built adapter-shaped from day one. Database-backed sessions, 30-day rolling (`updateAge` 24h). Both providers resolve to one `User` by verified email per the spec's linking rule — Google via `allowDangerousEmailAccountLinking` (safe here specifically because Google verifies email; the flag doesn't exist for the email provider, which unifies by construction since sign-in *is* an email lookup). Magic-link delivery (`src/lib/mailer.ts`) logs to console when `EMAIL_SERVER` is unset (dev) and throws if unset in production — no dedicated transactional-email provider chosen yet, that's still open. In-memory sliding-window limiter on the magic-link action (5/email, 20/IP per 15 min); flagged to swap for Redis before running >1 control-plane instance.

Route gating (`src/proxy.ts`) implements the spec's gating map as a pure classifier (`src/lib/route-access.ts`, unit tested) — public/auth/admin plus a separate age-attestation gate scoped to checkout + new-instance creation, not the whole dashboard, matching the spec's "purchase requires 18+" wording precisely. Landed on Next.js's new **Proxy** convention (`middleware.ts` renamed `proxy.ts`, per 16.2's deprecation) rather than the old name, since it's the same release we scaffolded on. Proxy always runs on Node.js (not Edge) — required here since `auth()` validates the database session against Postgres directly, which Edge can't do.

Verified end-to-end against live Postgres: full magic-link round trip (rate limit → CSRF → token issuance → console delivery → callback → session), single-use enforcement (replay correctly rejected), and all four gate outcomes (public passthrough, unauthenticated→`/login`, wrong-role→`/`, un-attested→`/account/attest-age`) exercised over HTTP against a running server, not just unit-tested in isolation. → `specs/06-auth.md`
