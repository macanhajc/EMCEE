## 2026-07-24 — Bot language: `general.bot_language` picks the locale for the bot's own built-in responses
User-requested follow-up to the Activation message feature above: "when a user asks for an emote the bot responds with some info, this should be translated to the bot's selected language." Scoped down to exactly that — the bot's own *built-in* responses (things the bot says on its own initiative that the owner never wrote), not the owner-authored templates (Welcome/VIP/Farewell/Activation message), which already stay in whatever language the owner typed them in via `_render`'s literal-token substitution and were deliberately left untouched here.

Audited every `send_whisper`/`.chat()` call site across all four engines (`emote.py`, `warden.py`, `avatar.py`, `greeter.py`) for hardcoded, non-owner-editable strings — 10 message keys plus 3 moderation-verb keys (mute/kick/ban, since `warden.action_denied`'s "Couldn't {action} {username} here" embeds the verb): emote's one-shot/loop-start/loop-timeout whispers and the `emotes` list header; warden's filter warning, mod-command "not found," and moderation-denied reply; avatar's anchor-not-standing and clone-insufficient-match whispers; greeter's one hardcoded string, VIP's `announce_to_room` public line (distinct from VIP's own owner-editable whisper template).

Added `general` — a new top-level schema section (`x-module: "general"`, packages/schemas/emcee/v1.json) for bot-wide settings that don't belong to any one feature module — with one field, `bot_language` (enum en/es/de/pt/ru matching apps/web's locale set, default `en`). New `workers/runtime/catalog/strings.py`: a `t(locale, key, **kwargs)` lookup table (`str.format` substitution, safe here since every value plugged in is internal/derived — an emote name, a username, a number — never an owner-authored template, unlike `_render`'s literal-token-only approach) covering all 13 keys across all 5 locales. `CatalogBot.bot_language` (`base.py`) reads `config.general.bot_language`, defaulting to English for a config row saved before this field existed. Every identified call site now renders through `t(self.bot.bot_language, ...)` instead of a fixed English literal.

Dashboard: new `GeneralCard` (shown as "Bot language"), `useGeneral` hook, `getGeneralConfig`/`updateGeneralConfig` actions — placed on the **Status** tab, not any module tab, since it's bot-wide (same instinct as `BotTokenUpdate`/`StatusLog`/`BotDangerZone` already living there). Auto-saves on change like every other single-field card, but needed neither the createPortal/useSyncExternalStore portal-form trick nor the manual-FormData-plus-forced-value workaround every `Checkbox`-driven auto-save card needs (Radix mirrors `checked` onto its hidden input asynchronously, after paint) — a plain native `<select>`'s value is already current in the DOM by the time its own `onChange` fires, so `new FormData(e.currentTarget.form)` just works. Seeded at instance creation from the creating user's own current dashboard locale (`instances/new/actions.ts`) — unlike the three template-copy fields seeded the same way, this isn't *localized copy*, the locale code itself **is** the value, so no `greeter-template-defaults.ts`-style translation table was needed for the seed, just the raw `AppLocale`.

Verified: 230/230 pytest (14 new — `test_strings.py`'s `t()`-helper unit tests including a completeness check that every key has all 5 locales, plus one bot-language-switch integration test per engine confirming existing English-default tests needed zero changes), 148/148 vitest, clean `tsc`/`eslint`.

## 2026-07-24 — Concierge: activation message — a public (not whisper) chat line on bot connect
User-requested feature: give the bot something to say publicly when it becomes active, explicitly *not* a whisper. Added as a new `activation_message` section (`x-module: "concierge"`) in `packages/schemas/emcee/v1.json`, alongside Welcome/VIP/Farewell — `enabled` (bool, default **false**), `template` (string, ≤200 chars, default "I'm online and ready to help in {room_name}!"), `cooldown_m` (int, 0–1440, default 10).

Runtime: `GreeterEngine.on_start` (`workers/runtime/catalog/greeter.py`), called from `EmceeBot.on_start` (`catalog/emcee.py`) right after `_room_name` is captured. Posts via `self.bot.highrise.chat(...)`, never `send_whisper` — there's no specific user to whisper to at connect time, so this is the one message in Concierge that's public by shape rather than public as an opt-in extra (VIP's `announce_to_room`, Farewell's `public_message`). Still off by default and cooldown-gated: the supervisor's reconnect-with-backoff loop (`supervisor.py`, cap ~5 min) reuses the same bot object — and therefore the same `GreeterEngine` instance — across every reconnect attempt, so without a cooldown a flapping connection would spam the room once per retry. Cooldown state (`_last_activation_at`) is in-memory on the engine, same pattern as `_last_greeted_at`; no DB round-trip needed since the object survives reconnects but not process restarts.

Dashboard: new `ActivationMessageCard`, `useActivationMessage` hook, `getActivationMessageConfig`/`updateActivationMessageConfig` actions — same self-contained-card shape as every other Greeter card (2026-07-24 entries above), rendered first in the Greeter tab (fires before any user ever joins). `template`'s locale-aware default extended into `lib/greeter-template-defaults.ts` (`activationMessageTemplate`, all 5 locales) and seeded at instance creation the same way Welcome/VIP/Farewell already are.

Verified with new pytest coverage in `test_greeter_bot.py` (off by default, public not whisper, custom template renders `{room_name}`, cooldown blocks a same-window repeat, `cooldown_m: 0` allows every reconnect) — 33/33 passing. Not yet click-tested in a live browser session (see the recurring "no credentials-based login in dev" gap noted in the instance-store entry below).

## 2026-07-24 — Instance store: one Zustand store for the whole `/instances/[id]` page, eager-loaded once
The per-card self-contained-hook architecture built out over the rest of this day (Emote → Activity, entries below) fixed prop-drilling but left a real UX bug: Radix's `Tabs.Content` unmounts inactive panels by default, so each card's local `useState`/`useEffect` data died on tab-away and refetched from scratch on tab-back — a reload + loading flash every revisit. Discussed with the user: fix with a store, eager (fetch everything once on page load, not lazily per tab visit), dependencies OK. Scope question — just `InstanceConfig`'s tab cards, or the whole page — the user explicitly chose **the whole page**: header (bot name/status/start-stop), `NotificationsCard`, `RoomInfoCard`, not only the six config tabs.

Added `zustand` (`^5.0.14`, first new runtime dependency of this migration). One store per page, `modules/instances/[id]/store.tsx`, two loading strategies for two kinds of data:
- `header`/`notifications`/`roomInfo` are **seeded synchronously** into the store's initial state from `page.tsx`'s existing server-side `Promise.all` fetch — this data was never inside a tab, so there's no reason to lose today's fast first paint; baking it into initial state (not a `useEffect`) means it's present on the very first render, SSR included.
- Every tab-card field (all 24, one per existing query action) is fetched once, eagerly, by a single `loadAll(instanceId)` action fired from a client-only mount effect — each write lands independently as its own request resolves, not blocked behind `Promise.all` on the slowest one.

**Not a module-singleton `create()` store** — self-caught before it could ship or be user-reported. `index.tsx` is a `"use client"` component, but Next.js still server-renders it to HTML per request; a plain module-level store would be one JS object shared across every concurrent request the Node process handles, and synchronously seeding it during render (needed to avoid the loading flash) would mean two different customers opening two different instances at the same moment could read or overwrite each other's data. Fixed with Zustand's documented Next.js pattern instead: `createStore` (vanilla, non-hook) + `React.createContext` + a `InstanceStoreProvider` that creates exactly one store via `useState(() => createStore(seed))` — one instance per component mount, i.e. one per SSR request, one per browser tab client-side. Two hooks off the same context: `useInstanceStore(selector)` (reactive, same calling convention as a plain `create()` hook — used by all 25 card hooks) and `useInstanceStoreImperative()` (raw `StoreApi`, for `.getState()`/actions outside render — the mount effect's `loadAll` call, and the header hook's success handler).

All 25 existing card hooks converted to read their `data` half from `useInstanceStore` instead of local `useState`, keeping their `useActionState`-driven mutate half unchanged except the success handler now calls `setSection(key, value)` instead of local `setState` — zero changes needed to ~22 of the ~25 card *components* themselves. `setBotRunning` and `updateEmailAlerts` converted from redirect-based to the established `ConfigActionState` pattern (same treatment as `replaceToken`/`replaceRoomId`/`requestModeration`, entries below) — a redirect remounts the page, which would now blow away the *entire* store, not just reset one tab, a stronger reason than before to avoid it. `NotificationsCard`/`RoomInfoCard` are now `{ instanceId }`-only, reading/writing through the store; `NotificationsCard`'s pre-existing optimistic-update pattern (write on click, never resynced from a server refetch) was deliberately preserved as-is, since it's a different, already-correct design choice from the "refetch after success" pattern every other mutation uses.

`store.ts` needed to be `store.tsx` once `InstanceStoreProvider` gained real JSX — caught live via a Turbopack parse error, not preemptively.

Verified via full `tsc`/`eslint`/`vitest run`/`next build` passes (148 tests, unchanged count — no new test files, this is a client-state refactor with no new business logic to unit-test). Did not get a live authenticated browser click-through: the dev DB has no credentials-based login (Auth.js database-session strategy, Google OAuth + magic link only) and inserting a temporary session row to fake one was declined in favor of the user checking manually — noted as a real verification gap, not a silent skip. Grepped for stray `setBotRunning` references and confirmed a `⨯ ReferenceError: setBotRunning is not defined` line in the dev server log was a transient artifact of Turbopack's incremental recompilation mid-edit (a `store.ts`-must-be-`.tsx` parse error at an earlier timestamp in the same log was confirmed real and already fixed) — the log's own later entries show clean compiles, and no bad reference exists in the current source.

## 2026-07-24 — Locale-aware default greeting templates
Every default value for `welcome.templates`/`vip.template`/`farewell.public_template` was hardcoded English in the schema's own `default` field — a genuine bot-facing bug once real customers exist, since a Portuguese- or Russian-speaking owner's bot would default to greeting guests in English until they noticed and rewrote it by hand. The schema can't hold five different defaults itself (it's shared with the Python runtime's own validation, which has no notion of dashboard locale), so this needed a TypeScript-only layer: `lib/greeter-template-defaults.ts` holds natural (not machine-translated-feeling) equivalents for all 5 locales, keeping `{username}`/`{room_name}` literal in every one (they're substituted by the runtime, not translated).

Applied in exactly one place — `instances/new/actions.ts`'s `createInstance`, keyed off the creating user's `getLocale()` — overriding `defaultsFromSchema(schema)`'s three English defaults before the initial insert. This is a **one-time seed at creation, not a live per-viewer thing**: the bot's greetings are what it actually says to Highrise guests, not something that should change depending on which locale someone happens to view the dashboard from later. `getWelcomeConfig`/`getVipConfig`/`getFarewellConfig` (actions.ts) also fall back to the localized default (via the *current viewer's* `getLocale()`) for the edge case of a section whose field genuinely doesn't type-check as saved — the same defensive fallback every other dedicated card action already has for schema drift, not a new mechanism.

This only affects instances created from this point on. ## 2026-07-24 — Avatar cards: converted every remaining uncontrolled field to controlled (root cause of "save reverted my emote pick")
Bug report: change the idle emote, press "Save idle emote," and it snaps back to the previous emote — but a page refresh shows the correct (new) one saved. Root cause: **React 19 resets uncontrolled fields inside a `<form action={...}>` back to their `defaultValue` once the action resolves successfully** — a deliberate feature mimicking a traditional form-submit-and-reload, documented as part of React 19's Actions work. `EmoteSelect` (`defaultValue={data.emote_id}`) is uncontrolled, so right after the save action resolves, React resets it to `defaultValue` — but at that exact instant, `data` (and thus `defaultValue`) hasn't been updated yet by the card's own post-save refetch, so it resets to the *stale, pre-save* value. Once the refetch does land moments later, nothing re-applies `defaultValue` again (React only honors it at mount / on genuine remount), so the stale display persists until a full page reload remounts everything fresh from the (correctly) persisted data.

This is systemic, not specific to the emote picker — every remaining uncontrolled field bound to one of these six cards' `useActionState`-driven forms was equally exposed. Fixed all of them, converting to controlled `value`/`onChange` seeded from `data` during render (the exact pattern `anchor-from-dashboard-card.tsx`'s x/y/z fields already used, for what — in hindsight — was almost certainly this same underlying issue):

- `EmoteSelect` (`emote-select.tsx`) — API changed from `defaultValue` to `value`/`onChange` outright; it has exactly one caller.
- `IdleEmoteLoopCard` — `emote_id`, `interval_s`.
- `ReactionBackCard` — `cooldown_s`.
- `OutfitCloneCard` — `min_match`.
- `AnchorFromDashboardCard` — `facing` (x/y/z were already controlled; this was the one field in that card still exposed).

Checked every other `defaultValue` in these cards' subcomponents (`TagListInput`, `OutfitPicker`, `PresetEditor`) — all three use it only to seed an *internal* `useState` once, with the actual submitted DOM element being an already-controlled hidden input (`value={...}`), which React's reset mechanism doesn't touch. No change needed there. Verified via full `tsc`/`eslint`/`vitest run`/`next build` passes.

## 2026-07-24 — Avatar cards: fixed a stale-checkbox race in auto-save-on-toggle (root cause of "save reverted the card to disabled")
Bug report: enable Idle emote loop, pick an emote, press "Save idle emote" — the card flips back to disabled. Root cause traced into Radix's `Checkbox` implementation (`@radix-ui/react-checkbox`, vendored under `radix-ui`): when `checked` is controlled, Radix renders a hidden native `<input type="checkbox">` (`CheckboxBubbleInput`) that carries the actual value for native form submission, and syncs it to the `checked` prop via a plain `React.useEffect` — a **passive effect that runs after paint**, not synchronously and not within a microtask.

Every enable-toggle handler across the six extracted Avatar cards did `setEnabled(checked); queueMicrotask(() => formRef.current?.requestSubmit())` — modeled on `notifications-card.tsx`'s email toggle, but that card's hidden input is a *separate*, plainly React-controlled `<input value={...}>` (updated synchronously in the normal commit, no Radix passive effect involved), not the Checkbox's own bubble input. Copying the pattern onto a case where the checkbox itself *is* the form-value source broke the assumption: the queued microtask fires before Radix's passive effect has flipped the hidden input's real DOM `.checked`, so `requestSubmit()` reads the *pre-toggle* value. The very first toggle silently saved the opposite of what the user just set — invisible at first because local React state (`enabled`) already showed the new value optimistically — and the very next save (auto or manual) reading that already-wrong persisted state, or a delayed refetch landing after further edits, is what surfaces as the toggle "reverting."

Fixed by not depending on reading the checkbox back out of the DOM at all: each card's `handleToggle` now builds `FormData` from the form directly (`new FormData(formRef.current)`, which still correctly picks up every other field via the HTML `form=` attribute) and explicitly forces `enabled` from the value just set in React state (`formData.set("enabled", "on")` / `.delete("enabled")`), then calls `formAction(formData)` directly — `useActionState`'s dispatch is callable standalone, not only as a `<form action>` target. Applied identically to `AnchorSpotCard`, `IdleEmoteLoopCard`, `ReactionBackCard`, `DefaultOutfitCard`, `OutfitPresetsCard`, `OutfitCloneCard`. `notifications-card.tsx` was checked and confirmed unaffected (different mechanism, not in scope regardless). Verified via full `tsc`/`eslint`/`vitest run`/`next build` passes.

Several of those descriptions are bot-command/template-variable documentation containing literal `<...>`/`{...}` syntax that was never meant to be ICU markup — e.g. Emote's `"\"all <emote>\" makes everyone in the room perform it as a staggered wave."` or Concierge's `"Use {username}, {room_name}."` (describing template variables *available to the customer's own config*, not something to interpolate here). ICU reads `<emote>` as an unclosed rich-text tag and `{username}` as a required interpolation argument nothing supplies — both throw. `sectionsFromSchema()` (`lib/schema-form.ts`) was always given a lookup function; `fieldSpecFor`'s design (fall back to the schema's own English text when a message key is *missing*) anticipated this being an override mechanism, not the always-hit path it turned out to be in practice.

**Why nothing caught this sooner:** `schema-form.test.ts` calls `sectionsFromSchema(emceeSchemaV1)` with no `t` argument at all, so it only ever exercises the plain-schema-fallback branch — never the real-translation branch that actually breaks. The other call site (`instances/[id]/actions.ts`) also passes no `t`, for the same reason (it only needs field shape, not display copy). `page.tsx`'s render path was the sole place a real translator ever reached these strings.

**Fix:** one call site, `tSchema.raw(path)` instead of `tSchema(path)` — `t.raw()` returns the message value verbatim, no ICU parsing, which is what field documentation text needs (it's copy to display, not a template to fill in). Added a comment on `SchemaCopyLookup` (`lib/schema-form.ts`) spelling out why, so a future "simplify this" pass doesn't quietly revert it back to `t()`.

**Known gap, not closed here:** no unit test guards this specific regression — doing so would mean exercising a real next-intl translator (`use-intl`'s `createTranslator`) against the actual `schemaEmcee` messages, and `use-intl` isn't a declared dependency of this app (only pulled in transitively through `next-intl`), so wiring that in felt like more surface than this bugfix warranted. Caught and confirmed only by hitting the real dev server before/after — verified via `.next/dev/logs/next-development.log`: seven `ERROR`-level next-intl parse failures on every pre-fix load, zero after, HTTP 200 both times (next-intl was catching its own parse errors and continuing the render, not crashing the page outright — the errors were console-only, matching what was reported). `tsc --noEmit`, `eslint .`, and the full `vitest` suite (131, unchanged — this path has no direct test coverage either way) all clean. Test session row and rendered fixture files cleaned up after. → `apps/web/src/lib/schema-form.ts`

## 2026-07-22 — Redis dropped entirely: config pub/sub moved to Postgres LISTEN/NOTIFY

R6 from `docs/cost-plan.md`, done as a follow-up to the same day's cost pass (R2–R5, entry below): removed Redis from the app completely, not just the already-dead heartbeat writes (R2). The only thing Redis still did after R2 was carry two pub/sub channels — `config.updated` and `avatar_position.updated` — and pub/sub is a service Postgres can provide itself via `LISTEN`/`NOTIFY` with no new infrastructure, so there was no longer a reason to run a second stateful service anywhere this app is deployed.

**Sender side unchanged in shape, different transport.** `apps/web/src/lib/redis.ts` → new `src/lib/notify.ts`, same two exported functions (`publishConfigUpdated`, `publishAvatarPositionUpdated`), same best-effort contract (catch-and-log, never throw — "the loop makes it correct even if a notification drops" still holds, unchanged from the Redis version). Each now runs `select pg_notify('<channel>', $1)` through the existing pooled `db` client (drizzle's `sql` tag, so the payload is a bound parameter, not string-interpolated SQL) instead of publishing to a Redis client. `instances/[id]/actions.ts`'s one import site updated; no behavior change from the action's point of view.

**Receiver side needed a real design decision Redis's client library didn't.** `redis.asyncio`'s `pubsub().listen()` is an async generator — `_listen_config_updates` could just `async for message in pubsub.listen()`. asyncpg's `LISTEN`/`NOTIFY` support is callback-based (`Connection.add_listener(channel, callback)`), and critically, **LISTEN is session-scoped**: a connection returned to a pool gets its subscriptions silently dropped on release (asyncpg's own pool reset issues an implicit `UNLISTEN`). New `db.connect_for_listen()` opens one dedicated, never-pooled `asyncpg.Connection` per supervisor process, held for its whole lifetime — `Supervisor.__init__` now takes this as an explicit `listen_conn` parameter alongside the normal `pool`, and `main()` creates and closes it alongside the pool. Also had to choose between a sync or `async def` callback: asyncpg schedules each `async def` callback as its own independent task, which would let two notifications for the same instance apply out of order or concurrently — the sync-callback-plus-`asyncio.Queue`-plus-single-consumer-loop shape in `_listen_config_updates` was chosen specifically to preserve the old generator's strictly-one-at-a-time-in-arrival-order semantics, not because it's the simpler asyncpg pattern.

**Channel names carried over unchanged** (`config.updated`, `avatar_position.updated`, dots and all) — Postgres NOTIFY channel names are plain strings via `pg_notify()`, and asyncpg quotes the identifier for the `LISTEN` command internally, so the dot needed no renaming or escaping on either side.

**Fully removed, not just unused:** the `redis`/`redis.asyncio` packages from both `apps/web/package.json` and `workers/runtime/pyproject.toml` (confirmed uninstalled from both environments via `pnpm install` and `uv sync`, not just deleted from the manifest); the `redis` service from `docker-compose.yml` (torn down locally, confirmed via `docker compose up -d --remove-orphans`) and from both CI job's service containers; `REDIS_URL` from every `.env.example`. `apps/web/src/lib/rate-limit.ts`'s comment about a future Redis-backed limiter was updated to say Postgres instead, since that's the only shared-state store this app has left.

**Verified for real, cross-plane, not just via the existing mocked/pytest-level pubsub tests rewritten to call `pg_notify` instead of `redis.publish`** (which was also done — `test_config_hot_apply_via_postgres_notify`, `test_config_rejection_keeps_last_good`, plus a new `test_avatar_position_update_via_postgres_notify` closing a coverage gap where the avatar-position channel had only ever been proven via a direct handler call, never through the actual LISTEN dispatch). Beyond the pytest suite (183 Python tests, all passing with `redis` fully uninstalled from the venv), ran a standalone script that starts the real `Supervisor` against real Postgres with a real dedicated `asyncpg` LISTEN connection, connects a real bot through the existing fake-Highrise-server test double, then shells out to `pnpm exec tsx` to invoke the **actual, unmodified `apps/web/src/lib/notify.ts` module** (not a Python-side stand-in for it) for both channels — confirming the real control-plane code's `pg_notify()` call reaches the real data-plane code's `add_listener` callback, dispatches to the correct handler by channel name, and produces the expected `config_applied`/`avatar_position_applied` events, with a clean supervisor shutdown after. The official SDK's `bot_runner()` compounds this — it waits on the server's first WebSocket reply with no timeout at all, so a room the bot can never actually join (bad room id, missing designer rights — exact platform behavior here is one of the highrise skill's "known unknowns") can leave that call hanging forever instead of erroring. Since the supervisor's whole backoff/`disconnected`/`degraded` escalation only ran *after* `bot_runner()` returned, a hang meant nothing ever got logged and nothing ever downgraded the status — a silent, permanent false-positive.

Fix: `status` now goes to `provisioning` first (an enum value the dashboard already had UI copy for — "Starting…" — but the supervisor never used). `CatalogBot._confirm_connected()` (`workers/runtime/catalog/base.py`), called from `EmceeBot.on_start`, is the real "this attempt actually reached Highrise" signal — the earliest one the SDK exposes. The supervisor races that signal against the connect attempt with a `connect_confirm_timeout_s` (default 20s, `workers/runtime/supervisor.py`); a stuck attempt gets cancelled, logs a new `connect_timed_out` event (surfaced in the dashboard's status log same as `disconnected`/`degraded`), and counts toward the existing consecutive-failures → `degraded` escalation regardless of how long the timeout window was — a repeatedly-hanging instance still reaches `degraded` in a bounded number of attempts instead of staying "Live" forever. `error_kind` still can't distinguish *why* (bad room vs. missing designer rights vs. a one-off platform hiccup) — the SDK still doesn't surface that, only stdout prints — so that part of the spec's open question stands. → `specs/04-bot-runtime.md`

## 2026-07-21 — Control plane: React error boundaries, Sentry crash reporting, PostHog analytics
`specs/05-security.md` already named Sentry ("both planes", `before_send` scrubber) as a decision, just not built yet on the control plane; this wires that up plus the App Router error-boundary convention and PostHog.

**Error boundaries are `app/error.tsx` + `app/global-error.tsx`, not a hand-rolled component.** This app is server-components-by-default (`CLAUDE.md`); a plain client-side `componentDidCatch` wrapper around `{children}` in the root layout would only catch client-render errors, missing the errors that actually matter here (Server Component/data-fetching failures). Next's file-based boundary convention *is* a React error boundary, automatically wrapping the segment tree — `error.tsx` catches route-level errors, `global-error.tsx` (renders its own `<html>/<body>`, per Next's requirement) catches errors from `layout.tsx` itself. Both share one fallback (`src/components/Elements/error-fallback.tsx`) and report via `Sentry.captureException` in a `useEffect` (fire-and-forget — the repo's `react-hooks/set-state-in-effect` lint rule blocks the setState-for-an-event-id pattern some Sentry docs show, so no event id is surfaced in the UI).

**Sentry scrubbing is structural (field-name), not a content regex, and that's a deliberate gap.** `specs/05-security.md` says "token pattern + known ciphertext/plaintext fields"; only the latter half is implemented (`src/lib/sentry-scrub.ts`, redacts any key matching `/token|secret|password|authorization|cookie/i` across request data/cookies/headers, breadcrumbs, extra, contexts). No Highrise token format is documented anywhere in this repo to pattern-match against, and `token-seal.ts` already never interpolates raw token values into thrown errors (the one thing structural redaction can't catch) — see its `TokenFormatError` split. If that discipline ever lapses, this scrubber won't save it.

**Next.js file conventions live under `src/`** (`instrumentation.ts`, `instrumentation-client.ts`), matching where `proxy.ts` already lives — confirmed Next 16.2 resolves both from `src/` before writing them. `sentry.server.config.ts`/`sentry.edge.config.ts` are plain modules imported by `instrumentation.ts`'s `register()`, gated on `NEXT_RUNTIME`. No `tracesSampleRate` set — this is error tracking only, not performance/APM, per the actual ask; `onRouterTransitionStart` is still exported because the SDK requires it for navigation context on crash reports regardless of tracing being on.

**PostHog: `capture_pageview: 'history_change'`, `person_profiles: 'identified_only'`, `disable_session_recording: true` always on**, wired as a thin client provider (`posthog-provider.tsx`) that no-ops when `NEXT_PUBLIC_POSTHOG_KEY` is unset. Session recording is off outright rather than relying on input masking — belt-and-suspenders given the token-paste field is the app's one truly sensitive UI surface (already `type="password"`, so autocapture wouldn't record its value either way). No `posthog-node`/server-side capture added — out of scope for what was asked, and this app's server actions don't have an established analytics-event convention yet to hang it on.

Verified: full `next build` (Turbopack) clean, `tsc --noEmit` and `eslint .` clean across the whole app. Confirmed the boundary wiring against the real dev server (not just the build): a route that throws in a Server Component gets caught (logged server-side, 500 returned) and the RSC payload correctly references `app/error.tsx` as that route's boundary component. ## 2026-07-21 — Crash-loop email alerts + a general operational status log
Closes the gap between what `specs/04-bot-runtime.md`'s failure catalog already promised ("`degraded`, alert us, customer sees honest status") and what actually existed: crash isolation and detection were already solid (`catalog/base.py`'s handler shielding, `supervisor.py`'s backoff + `degraded` escalation, `instance_events` logging every step) but nothing ever told the *customer* — no email, no notification of any kind, grepped the whole repo to confirm. **Keys off `instance_events`, not `bot_instances.status`.** Read `supervisor.py`'s `_run_instance_loop` closely before designing detection: `status` is written to `"running"` optimistically at the start of *every* connect attempt, even mid-crash-loop, so it bounces running↔degraded rather than holding level — polling it directly would flake depending on timing. Known, deliberate v1 trim: the cooldown resets from *last alert sent*, not from outage onset, so a recovery-then-re-crash inside that 30-minute window defers the reminder rather than firing instantly; a true incident-boundary detector would need episode/gap-grouping over the event history, more machinery than a v1 alert needs. **Delivery reuses the existing Resend account**, via a new sibling to `mailer.ts` (`lib/instance-alert-mailer.ts`) rather than extending it — `mailer.ts`'s docblock scopes it to the Nodemailer auth provider specifically. Same fallback discipline: unset `RESEND_API_KEY` logs to console in dev, throws in production, since a silently-not-alerting alert system is exactly the failure this feature exists to prevent. The route itself never lets one instance's send failure abort the batch (per-candidate `try/catch`) and only records the dedup marker on a *successful* send, so a transient Resend failure retries next tick instead of going dark.

**Second gap closed the same pass:** `ActivityLog`/`getRecentModerationEvents` (`warden-events.ts`) only ever surfaced `kind = "moderation"` rows and is Warden-specific in spirit, even though it renders unconditionally. ## 2026-07-20 — Concierge visit-stats persistence: `greeter_visits` table, generic `db_pool` capability on every catalog bot
Fourth pass on Concierge the same day. Visit counts were in-memory-per-process since the original build — every reconnect or redeploy reset `{visit_count}` and farewell's `min_visits` to zero, an explicitly flagged known gap rather than an oversight. Closed it.

ON CONFLICT (bot_instance_id, user_id) DO UPDATE SET visit_count = greeter_visits.visit_count + 1 ... RETURNING visit_count` — no read-then-write race between concurrent joins.

Verified against real Postgres, not mocked: `test_db.py` gained three tests for `record_visit` (increments correctly, independent per instance × user, username updates on revisit — the dashboard "regulars" table this feeds isn't built yet, but the data is real and queryable). `test_greeter_bot.py` gained two integration-level tests — one constructs two separate `EmceeBot` objects backed by the same real `bot_instance_id` and confirms the second correctly reads "visit #2" from what the first wrote (proving actual cross-restart survival, not just that the SQL is well-formed), and one wires a pool whose `.acquire()` raises and confirms the greeting still sends with a session-local count instead of going silent. ## 2026-07-20 — Emcee merge: Concierge folded into one bot/instance/token with Emote; control plane wired end-to-end
Third pass on Concierge the same day (brainstorm → build → this). Asked to wire Concierge into the control plane the way Emote already was — seed it into `catalog_bots`, hook up the dashboard — and the naive version of that broke the product's own stated model. Every spec (`emote.md`, `greeter.md`, `avatar.md`) says feature modules share one bot/instance/token; the code had `EmoteBot` and `GreeterBot` as two independent `CatalogBot` subclasses with their own slugs. Chosen fix, picked over two cheaper alternatives (a real bot-picker UI accepting the two-separate-products model; or seeding the row without exposing it anywhere yet) after asking: **merge the runtime**, matching what the specs already promised.

**Python (`workers/runtime/catalog/`):** `EmoteBot`/`GreeterBot` demoted from `CatalogBot` subclasses to plain `EmoteEngine`/`GreeterEngine` classes that read/write through an owning bot (`self.bot.highrise`/`.throttle`/`.config`/`._room_owner_id`). New `emcee.py`'s `EmceeBot(CatalogBot)`, `SLUG = "emcee"`, composes both engines behind one connection/throttle/config and is the only thing whose handlers `CatalogBot.__init_subclass__`'s shielding actually wraps — each handler just dispatches into the relevant engine(s), `on_user_leave` into both (Emote cancels the leaver's loop, Concierge logs a farewell). Supervisor's `CATALOG` now has one entry, `{"emcee": EmceeBot}`. Existing tests (`test_emote_bot.py`, `test_greeter_bot.py`) construct `EmceeBot` and reach into `bot._emote.*`/`bot._greeter.*` for internals that used to be direct attributes — mechanical, not rewritten.

**Schema:** `emote/v1.json` + `greeter/v1.json` merged into one `packages/schemas/emcee/v1.json`, all 7 sections flat (no schema-level module boundary), each tagged `"x-module": "emote"` or `"concierge"` — a vendor-extension keyword the dashboard reads for tab grouping, meaningless to validation. Ajv's strict mode rejects unrecognized keywords by default (`"strict mode: unknown keyword: x-module"`, caught by the web test suite immediately) — registered via `ajv.addVocabulary(["x-module"])` rather than disabling `strict` wholesale, which would've also relaxed real correctness checks. Python's `jsonschema` never had this problem — unrecognized keywords are spec-legal and silently ignored, no strict mode to fight.

**Second real gap the merge surfaced, not introduced by it:** Concierge's schema needed bare `type: "string"` leaves (`vip.template`, `quiet_hours_start/end/tz`, `farewell.public_template`) that `schema-form.ts`'s `fieldSpecFor` had never supported — it only recognized enum/boolean/integer/array, silently returning `null` (and dropping the field entirely, comment and all: *"extend when a bot needs one"*) for anything else. Left alone, saving *any* config change on Concierge would have submitted a form missing those fields' inputs entirely, silently blanking them in storage on every save — not a hypothetical, a guaranteed data-loss bug on the very first save. Added a `"string"` `FieldSpec` kind end to end: `fieldSpecFor`, `parseConfigFormData`, and a plain text `<Input>` in `instance-config.tsx`.

**Dashboard tabs:** `InstanceConfig` already had a `BOT_ROADMAP`-driven tab bar with disabled "coming soon" placeholders — Concierge just needed to become a live one. The trap here: Radix's `TabsContent` unmounts inactive panels by default, so putting each module's `SectionCard`s inside real `TabsContent` blocks would mean submitting the form while on the Emotes tab silently drops every Concierge field from the `FormData` (and vice versa) — wiping the other module's saved config on every save. Fixed by keeping one shared `<form>` outside any `TabsContent`, with module visibility toggled by a plain Tailwind `hidden` class off local `activeModule` state — same "hidden, not unmounted" idiom `SectionCard` already used one level down for its own enabled-toggle sub-fields. Radix `Tabs`/`TabsList`/`TabsTrigger` still drive the tab-button UI/UX; only the content-mounting semantics were avoided. `BOT_ROADMAP` lost its `Concierge` entry (real tab now); `roadmap.ts`, `how-it-works.tsx`, and the hero mockup caption updated for accuracy.

**Data migration, not just seed:** the existing local dev DB had real `bot_instances` rows on `catalog_bot_slug = 'emote'` — a rename needed an actual migration (`drizzle/0003_rename_emote_to_emcee.sql`), not just changing what `seed.ts` inserts going forward. Order matters under the FK: insert the `emcee` row (additive), repoint `bot_instances` to it, drop the `emote` row — satisfies the FK at every intermediate step, not just the end. `ON CONFLICT DO UPDATE` rather than `DO NOTHING` on the insert, because the Python test suite's `conftest.py` fixture inserts a bare-bones `catalog_bots` placeholder against this same shared dev DB on every run (did the same for `emote` before this rename) — `DO NOTHING` would've left that placeholder's null tagline/price-ids in place over the real data. `STRIPE_EMOTE_*_PRICE_ID` env vars renamed to `STRIPE_EMCEE_*` (`.env` + `.env.example`) — same underlying Stripe objects, the real product was already named "Emcee (Emote Bot)" in the sandbox, this just stopped the env var name from lying about it.

Verified for real, not just by reasoning about it: ran the actual migration against the live local Postgres (`docker exec` before/after queries confirmed the row rename and both existing instances' `catalog_bot_slug` flip); re-ran `seed.ts` and confirmed idempotency; full suites green (98 Python, 87 web, `tsc --noEmit` clean, `eslint` clean); then — since no browser-automation tool was available this turn — inserted a real session row directly into Postgres, hit `/dashboard`, `/instances/new`, and a real `/instances/[id]` through the actual running dev server with `curl` and that session cookie, and confirmed the rendered HTML: correct Emcee tagline, `BOT_ROADMAP` no longer lists Concierge, and the config page's real form field names (`welcome.enabled`, `vip.template`, `vip.users`, `farewell.min_visits`, `quiet_hours_tz`) plus both `Emotes` and `Concierge` tab labels are actually present in server output. Didn't click through in an actual browser (no tool for it this turn) — SSR output and the field-level round-trip is proven, live client-side tab-switching interaction isn't. Test artifacts (session, user, instance) cleaned up after. → `specs/bots/emote.md`, `specs/bots/greeter.md`, `specs/04-bot-runtime.md`

## 2026-07-20 — Loop/stop: EmoteBot's first post-v1 feature, off by default
Moved loop/stop out of `specs/bots/emote.md`'s "explicitly deferred" list and built it (`workers/runtime/catalog/emote.py`): `loop <emote>` repeats it for the speaker on an interval until `stop`, leaving the room, or a safety timeout; `stop` is a distinct word from emote-all's `stopall` (no collision) and only ever stops the caller's own loop, no permission check needed since it's inherently self-service.

Extended the shared config schema (`packages/schemas/emote/v1.json`) additively — a new `loop` section with `enabled` (**default false**, unlike the other three sections' default-true — this is explicitly the heaviest sustained-load feature per the spec's own words and isn't tuned against real limits, so it's opt-in), `interval_s`, `max_concurrent_loopers` (the spec explicitly called out needing this), `max_duration_s` (a safety auto-stop for a forgotten/orphaned loop, e.g. a disconnect that never fires a clean leave — whispers the user why when it fires), and `cooldown_s`. Purely additive (every new field optional with a default), so no schema version bump — same v1, still validates old stored configs unchanged. This is the first real test of "schema is the shared contract": the TS control plane's schema-driven form (`sectionsFromSchema`/`defaultsFromSchema`) picked up the new section with zero code changes, only test updates (the tests that assert the schema's *exact* section/default list, not the generic renderer itself).

Design decisions made explicit rather than left implicit: starting a new loop while already looping *switches* the emote (cancels old, starts new) rather than stacking a second loop or requiring `stop` first — and doesn't count against `max_concurrent_loopers` since it's not adding a looper. The switch-cleanup race (old task's `finally` running after a new task has already replaced it in `self._loops`) is handled with a compare-and-delete (`if self._loops.get(user_id) is task: pop(...)`) rather than an unconditional pop, which would otherwise sometimes delete the *new* task's dict entry. Blocked-by-cap attempts get a quiet whisper explaining why, unlike genuinely-unknown text which stays silent — this is a recognized command being capped, not gibberish, and silent failure on a paying customer's bot would read as broken. `on_user_leave` is now overridden (previously not) purely to cancel the leaver's own loop — emote-all still doesn't track roster via join/leave events, it snapshots fresh via `get_room_users()` at trigger time, cheaper and can't drift.

Verified with 13 new unit tests against the same `FakeHighrise` pattern (start/repeat, unknown emote, stop scoping to the caller only, start-cooldown, emote-switching including the cleanup race, cap enforcement and its whisper, cap *not* blocking an existing looper's switch, natural auto-stop via `max_duration_s` with its whisper, `on_user_leave` cancellation). One test bug caught during the first run, not a code bug: asserting on `self._loops[user_id]` *after* stopping a loop 404s, because the loop's own cleanup already removed it by then — fixed by capturing the task reference before cancelling, which is itself a small confirmation that the cleanup-on-stop design works as intended.

## 2026-07-20 — Python supervisor wired; lease-based claiming; verified via a protocol-compliant fake Highrise server
Built the real reconciliation loop (`workers/runtime/supervisor.py`): claim → spawn → heartbeat → hot-apply → stop, against real Postgres (`db.py`, plain asyncpg, no ORM) and real Redis (`heartbeat.py`). Resolved the shard-assignment open question in favor of the spec's own lean — lease-based claiming (`bot_instances.supervisor_id` + `lease_expires_at`, new migration `0002_add_lease_claiming`), atomic via `FOR UPDATE SKIP LOCKED`, so a crashed supervisor's instances get picked back up on the next claim cycle with no ops action. Tokens are decrypted fresh on every (re)connect attempt, not just once at spawn — that's what makes "replace token" take effect without a dedicated push signal.

No real Highrise bot token or room exists in this environment (Trust & Safety gated, no zero-registration bootstrap unlike Stripe's sandbox) — verification instead used a small fake WebSocket server (`tests/fake_highrise_server.py`) speaking the real wire protocol (`_type`-tagged JSON via cattrs, confirmed by reading `highrise/_unions.py` and `highrise/models.py` directly) against the **actual SDK's `bot_runner()`** via its `HR_BOTAPI_URL` env override, not a mock of our own code. Reading `highrise/__main__.py` also surfaced a genuinely useful fact: `bot_runner()` internally retries `ConnectionResetError`/`WSServerHandshakeError`/`TimeoutError` forever via its own throttler and only ever *returns* on a fatal `do_not_reconnect` application error — meaning the supervisor's own backoff/degraded escalation is correctly scoped to fatal credential/room-class failures, not network blips, which the SDK already absorbs invisibly. This directly shaped the design rather than being incidental — see the open-questions update in `specs/04-bot-runtime.md` on why precise `error_kind` classification isn't achievable yet (the SDK gives no structured reason for a fatal return, only stdout prints).

26 Python tests: DB-layer lease/claim semantics against real Postgres including a genuine two-pool concurrency test proving two supervisors never double-claim; five live tests driving the real `bot_runner()` against the fake server (connect → running status → heartbeat; desired_state flip → graceful stop; fatal token → degraded after N fast failures; config.updated hot-apply, both accepted and rejected); five unit-level edge cases (unknown catalog slug, multi-tick reconcile stability, shutdown draining, malformed/unrelated pub/sub payloads). Then ran `supervisor.py` itself as a real OS subprocess (not a pytest call) against the fake server: claimed a real instance, connected, wrote a real heartbeat, and on a real SIGTERM drained gracefully (lease released, heartbeat cleared, `status='stopped'`, event emitted, clean exit code) — proving the CLI entrypoint and signal handling, not just the orchestration logic.

Two real bugs found by the live tests, not caught by writing the code carefully the first time: (1) `self.running` was keyed by `row["id"]`, which asyncpg returns as `uuid.UUID`, while the Redis pub/sub payload's `instanceId` is always a JSON string — every hot-apply lookup would have silently no-op'd in production. Fixed by normalizing to `str()` at the one place instance ids enter the supervisor's own state. (2) `highrise.__main__` imports `pkg_resources` at module load without declaring `setuptools` as a runtime dependency, and modern `setuptools` no longer bundles it — pinned `setuptools<81`, logged as a real fragility in `specs/04-bot-runtime.md` since that pin may not stay satisfiable indefinitely.

Known gap: nothing here has touched the actual Highrise platform — no real rate limits, error message shapes, or protocol quirks are confirmed. That's explicitly deferred to a canary instance once real bot credentials exist, matching the spec's own "measure real platform limits" posture. → `specs/04-bot-runtime.md`

## 2026-07-20 — Instance creation flow: paste-token → seal → config form → Redis wake
End-to-end BotInstance lifecycle from the dashboard: `/instances/new` picks a catalog bot from the real `catalog_bots` table (only `emote` today), takes a room ID or share link (normalized — last path segment if a URL was pasted) and a token, seals it via `sealToken()`, and inserts with `config` set to the schema's own declared defaults. `desiredState`/`status` are left at their DB defaults (`stopped`/`created`) — creation never flips them, since only billing may (`specs/02-architecture.md`); the instance page says so plainly ("awaiting checkout") rather than pretending the bot is live.

`/instances/[id]` renders a config form **generated from the JSON Schema**, the architecture spec's core leverage claim, now real: `sectionsFromSchema`/`defaultsFromSchema`/`parseConfigFormData` (`src/lib/schema-form.ts`) walk the schema's fixed two-level shape (object of sections → primitive leaves) rather than a fully general recursive JSON Schema walker — extend when a bot config actually needs deeper nesting. Save path is exactly the spec's words: validate (`ajv`, `src/lib/schema-validate.ts`) → write Postgres → publish `config.updated` on Redis (payload carries only the instance id — Postgres stays sole source of truth, publish failures are swallowed since "the loop makes it correct even if pub/sub drops," `specs/04-bot-runtime.md`). Two bugs the build/tests didn't catch, found only by driving the real flow end-to-end:
- `sealToken()`'s catch-all conflated "bad token format" with "server misconfigured" (e.g. `TOKEN_SEAL_PUBLIC_KEY` unset) into the same misleading "that token doesn't look right" message. Split into a distinguished `TokenFormatError`; anything else now surfaces as a real error instead of blaming the user for our config.
- The config form's `<input type="number" min max>` means real users can never submit an out-of-range value — the browser blocks it before JS or the server sees it. Server-side rejection of the same value is still covered (`schema-validate.test.ts` against the live schema), but that's now known to be a defense-in-depth backstop against a hostile client, not a path a real user can hit through the UI.

Verified with a real headless-Chromium run (Playwright driving system Chrome, not a mock) against live Postgres + Redis: full click-through — sign in, attest age, create instance, view schema-rendered defaults, save a config change, replace the token — then confirmed independently: the Redis subscriber actually received `config.updated`; Postgres held the submitted config verbatim; **a second signed-in user hitting the first user's `/instances/[id]` got a 404**, proving `getOwnedInstance`'s tenant scoping; and the replaced token's stored ciphertext was decrypted through the real `tokenbox.py` (separate process, separate keypair half) to the exact replacement value — the strongest possible proof the two-plane token design (`fd10d1a`) holds under a real write, not just the original cross-plane script's synthetic round trip.
