# Decision log

ADR-lite. Newest first. One entry per decision that shapes the product or architecture; link the spec that carries the detail.

## 2026-07-20 — Loop/stop: EmoteBot's first post-v1 feature, off by default
Moved loop/stop out of `specs/bots/emote.md`'s "explicitly deferred" list and built it (`workers/runtime/catalog/emote.py`): `loop <emote>` repeats it for the speaker on an interval until `stop`, leaving the room, or a safety timeout; `stop` is a distinct word from emote-all's `stopall` (no collision) and only ever stops the caller's own loop, no permission check needed since it's inherently self-service.

Extended the shared config schema (`packages/schemas/emote/v1.json`) additively — a new `loop` section with `enabled` (**default false**, unlike the other three sections' default-true — this is explicitly the heaviest sustained-load feature per the spec's own words and isn't tuned against real limits, so it's opt-in), `interval_s`, `max_concurrent_loopers` (the spec explicitly called out needing this), `max_duration_s` (a safety auto-stop for a forgotten/orphaned loop, e.g. a disconnect that never fires a clean leave — whispers the user why when it fires), and `cooldown_s`. Purely additive (every new field optional with a default), so no schema version bump — same v1, still validates old stored configs unchanged. This is the first real test of "schema is the shared contract": the TS control plane's schema-driven form (`sectionsFromSchema`/`defaultsFromSchema`) picked up the new section with zero code changes, only test updates (the tests that assert the schema's *exact* section/default list, not the generic renderer itself).

Design decisions made explicit rather than left implicit: starting a new loop while already looping *switches* the emote (cancels old, starts new) rather than stacking a second loop or requiring `stop` first — and doesn't count against `max_concurrent_loopers` since it's not adding a looper. The switch-cleanup race (old task's `finally` running after a new task has already replaced it in `self._loops`) is handled with a compare-and-delete (`if self._loops.get(user_id) is task: pop(...)`) rather than an unconditional pop, which would otherwise sometimes delete the *new* task's dict entry. Blocked-by-cap attempts get a quiet whisper explaining why, unlike genuinely-unknown text which stays silent — this is a recognized command being capped, not gibberish, and silent failure on a paying customer's bot would read as broken. `on_user_leave` is now overridden (previously not) purely to cancel the leaver's own loop — emote-all still doesn't track roster via join/leave events, it snapshots fresh via `get_room_users()` at trigger time, cheaper and can't drift.

Verified with 13 new unit tests against the same `FakeHighrise` pattern (start/repeat, unknown emote, stop scoping to the caller only, start-cooldown, emote-switching including the cleanup race, cap enforcement and its whisper, cap *not* blocking an existing looper's switch, natural auto-stop via `max_duration_s` with its whisper, `on_user_leave` cancellation). One test bug caught during the first run, not a code bug: asserting on `self._loops[user_id]` *after* stopping a loop 404s, because the loop's own cleanup already removed it by then — fixed by capturing the task reference before cancelling, which is itself a small confirmation that the cleanup-on-stop design works as intended.

## 2026-07-20 — EmoteBot logic: real handlers, a doc-verified starter catalog, no fabricated emote list
Built the v1 core loop (`workers/runtime/catalog/emote.py`): emote-on-say (per-user cooldown, `disabled_emotes`), `emotes`/`!emotes` whispered list (paginated by character budget), and `all <emote>` (owner/owner_designers/allowlist permission via `self.highrise.get_room_privilege` + the room owner id captured from `on_start`'s `SessionMetadata`, room-wide cooldown, `get_room_users()` snapshot-at-trigger fan-out through the BACKGROUND throttle class, `stopall` abort via task cancellation).

Read the actual SDK source before writing anything, per the highrise skill's own instruction, and it paid off twice: (1) `highrise/webapi.py` has **no emotes endpoint at all** — confirms the spec's "known unknown" outright: there is no live source of truth for emote ids, only a maintained static list, ever. (2) `self.highrise.get_room_privilege(user_id)` exists and does exactly what `owner_designers` permission needs — found by reading `highrise/__init__.py` rather than assuming it didn't exist.

The catalog itself (`catalog/emotes.json`) is a deliberately small, **doc-verified** 5-entry starter set — every id confirmed against Highrise's own docs (create.highrise.game/learn/bots/api/endpoints/emoterequest via WebFetch), not a fabricated "looks plausible" full list. Highrise publishes no comprehensive emote_id catalog anywhere, official or community (checked the createforum thread and a couple of community bot repos too — nothing). `targetable: true` on all 5 is carried through as an explicit, flagged *assumption* (the docs describe targeting generally, not per-emote), matching exactly what the spec's own "Verification list" already called out as needing real testing. Aliases, including PT-BR ones, are our own product judgment (not a platform fact) with accent-folding (`unicodedata` NFKD) so "olá"/"ola" both resolve without listing every accented form twice.

Found and fixed a real gap in `catalog/base.py` while implementing this: `on_start` — which `EmoteBot` now overrides to capture the room owner id — wasn't in the shielded-handler list, so an exception there could have torn down the whole connection instead of being safely contained like every other handler. Added it.

Surfaced, not silently resolved: the emote-all fan-out shares the single per-instance action throttle with emote-on-say, so it runs at whatever the (still-conservative, unverified) default throttle rate allows — slower than this spec's own "~2-4 users/sec" target. Picking a second unverified "fan-out rate" to hit that number wouldn't actually fix anything; logged as the same open "tune with saturation telemetry" item already in `specs/04-bot-runtime.md`, now with a concrete tension between two spec numbers to resolve together.

Verified with 33 new unit tests (9 catalog + 24 bot-behavior; 59 total across the whole Python test suite now) against a `FakeHighrise` that records every `send_emote`/`send_whisper`/`get_room_users`/`get_room_privilege` call with exact arguments — covering every permission tier, cooldown (per-user and room-wide, independently), `disabled_emotes`, accent/alias resolution, snapshot-at-trigger semantics, `get_room_users` error handling, and a genuine mid-wave `stopall` cancellation (slowed the throttle to catch the wave truly in flight, not finished or not-yet-started). Did not extend the live fake-WebSocket-server proof from the supervisor turn to this feature's send-side wire format — doing so needs request/response ACK correlation for several message types, which is SDK-internal plumbing rather than the business logic this turn actually changed; the `FakeHighrise` tests already assert exact call arguments, which is the real risk surface for this code. Noted as a real, intentional verification boundary, not an oversight.

Known gap, same shape as the supervisor turn: nothing here has touched the real platform, so per-emote targetability, burst tolerance, and exact wire behavior remain unconfirmed until a canary instance exists. → `specs/bots/emote.md`

## 2026-07-20 — Python supervisor wired; lease-based claiming; verified via a protocol-compliant fake Highrise server
Built the real reconciliation loop (`workers/runtime/supervisor.py`): claim → spawn → heartbeat → hot-apply → stop, against real Postgres (`db.py`, plain asyncpg, no ORM) and real Redis (`heartbeat.py`). Resolved the shard-assignment open question in favor of the spec's own lean — lease-based claiming (`bot_instances.supervisor_id` + `lease_expires_at`, new migration `0002_add_lease_claiming`), atomic via `FOR UPDATE SKIP LOCKED`, so a crashed supervisor's instances get picked back up on the next claim cycle with no ops action. Tokens are decrypted fresh on every (re)connect attempt, not just once at spawn — that's what makes "replace token" take effect without a dedicated push signal.

No real Highrise bot token or room exists in this environment (Trust & Safety gated, no zero-registration bootstrap unlike Stripe's sandbox) — verification instead used a small fake WebSocket server (`tests/fake_highrise_server.py`) speaking the real wire protocol (`_type`-tagged JSON via cattrs, confirmed by reading `highrise/_unions.py` and `highrise/models.py` directly) against the **actual SDK's `bot_runner()`** via its `HR_BOTAPI_URL` env override, not a mock of our own code. Reading `highrise/__main__.py` also surfaced a genuinely useful fact: `bot_runner()` internally retries `ConnectionResetError`/`WSServerHandshakeError`/`TimeoutError` forever via its own throttler and only ever *returns* on a fatal `do_not_reconnect` application error — meaning the supervisor's own backoff/degraded escalation is correctly scoped to fatal credential/room-class failures, not network blips, which the SDK already absorbs invisibly. This directly shaped the design rather than being incidental — see the open-questions update in `specs/04-bot-runtime.md` on why precise `error_kind` classification isn't achievable yet (the SDK gives no structured reason for a fatal return, only stdout prints).

26 Python tests: DB-layer lease/claim semantics against real Postgres including a genuine two-pool concurrency test proving two supervisors never double-claim; five live tests driving the real `bot_runner()` against the fake server (connect → running status → heartbeat; desired_state flip → graceful stop; fatal token → degraded after N fast failures; config.updated hot-apply, both accepted and rejected); five unit-level edge cases (unknown catalog slug, multi-tick reconcile stability, shutdown draining, malformed/unrelated pub/sub payloads). Then ran `supervisor.py` itself as a real OS subprocess (not a pytest call) against the fake server: claimed a real instance, connected, wrote a real heartbeat, and on a real SIGTERM drained gracefully (lease released, heartbeat cleared, `status='stopped'`, event emitted, clean exit code) — proving the CLI entrypoint and signal handling, not just the orchestration logic.

Two real bugs found by the live tests, not caught by writing the code carefully the first time: (1) `self.running` was keyed by `row["id"]`, which asyncpg returns as `uuid.UUID`, while the Redis pub/sub payload's `instanceId` is always a JSON string — every hot-apply lookup would have silently no-op'd in production. Fixed by normalizing to `str()` at the one place instance ids enter the supervisor's own state. (2) `highrise.__main__` imports `pkg_resources` at module load without declaring `setuptools` as a runtime dependency, and modern `setuptools` no longer bundles it — pinned `setuptools<81`, logged as a real fragility in `specs/04-bot-runtime.md` since that pin may not stay satisfiable indefinitely.

Known gap: nothing here has touched the actual Highrise platform — no real rate limits, error message shapes, or protocol quirks are confirmed. That's explicitly deferred to a canary instance once real bot credentials exist, matching the spec's own "measure real platform limits" posture. → `specs/04-bot-runtime.md`

## 2026-07-20 — Stripe checkout wired against a real sandbox account

Confirmed via the Stripe implementation-planner tool that the spec's existing choices (hosted Checkout in `mode: subscription`, flat-rate pricing, trial-with-card, Customer Portal, default Smart Retries) were already the right answers — no course correction needed. Created a real Product ("Emcee (Emote Bot)") with two BRL Prices (R$39/mo, R$390/yr) matching the spec's draft numbers; ids live in `.env.example` alongside the sandbox account.

Built: `startCheckout` (creates a real subscription-mode Checkout Session — `client_reference_id` = instance id, `subscription_data.metadata` carries instance+user id for later event correlation, trial granted only if `trial_registry` has no prior row for this room+token), `openBillingPortal` (Customer Portal session), and the webhook handler (`api/webhooks/stripe/route.ts`) with a strict division of responsibility: `checkout.session.completed` links the purchase and flips `desired_state`; `customer.subscription.*` is the *sole* writer of the status mirror and all subsequent `desired_state` decisions (via `mapSubscriptionStatus`, unit-tested against all 8 Stripe subscription statuses); `invoice.*` is audit-trail only. The handler never touches `bot_instances.status` — that stays supervisor-owned per the architecture split. Idempotency via `webhook_events` PK-on-event-id; a `trial_registry` row is written on webhook confirmation of an actual trial grant, not at checkout-session creation, so an abandoned checkout never burns eligibility. Deliberately omitted `automatic_tax` (no Stripe Tax registration — CNPJ/contador blocker) and `payment_method_types` (best practice: let Stripe determine eligible methods dynamically) from the Checkout Session, per Stripe's own best-practices guidance.

Verified against the live sandbox, not mocks: a real Playwright-driven purchase through Stripe's actual hosted test checkout (card 4242...4242) — Stripe's own UI showed "Start trial" confirming the trial wired correctly, and the resulting real Subscription object confirmed `trial_end - trial_start` = exactly 604800s, correct BRL price, correct metadata. Since the MCP tool doesn't expose the Events API either, fetched the real event payloads directly via the `stripe` SDK with the same key and replayed them (self-signed with a local-only webhook secret, `Stripe.webhooks.generateTestHeaderString`) against the actually-running local webhook endpoint: correct processing, correct idempotent no-op on replay, correct 400 on a tampered signature. Resulting DB state confirmed row-by-row: `subscriptions` mirror correct, `bot_instances.desired_state` → `running` while `status` stayed untouched, `users.stripeCustomerId` captured, `instance_events` audit trail complete with zero sensitive data, `trial_registry` populated. The Customer Portal button was confirmed to reach a real `billing.stripe.com` session.

Known gap, logged in `specs/03-billing.md`: no live webhook endpoint is registered anywhere (needs a public URL), so Stripe's actual delivery/retry behavior is unexercised — today's proof is that the handler is correct given a real event, not that Stripe can reach it yet. Pix also isn't enabled on this sandbox (test-account default), so Pix-specific behavior remains an open verification item for the real BR account. → `specs/03-billing.md`

## 2026-07-20 — Instance creation flow: paste-token → seal → config form → Redis wake
End-to-end BotInstance lifecycle from the dashboard: `/instances/new` picks a catalog bot from the real `catalog_bots` table (only `emote` today), takes a room ID or share link (normalized — last path segment if a URL was pasted) and a token, seals it via `sealToken()`, and inserts with `config` set to the schema's own declared defaults. `desiredState`/`status` are left at their DB defaults (`stopped`/`created`) — creation never flips them, since only billing may (`specs/02-architecture.md`); the instance page says so plainly ("awaiting checkout") rather than pretending the bot is live.

`/instances/[id]` renders a config form **generated from the JSON Schema**, the architecture spec's core leverage claim, now real: `sectionsFromSchema`/`defaultsFromSchema`/`parseConfigFormData` (`src/lib/schema-form.ts`) walk the schema's fixed two-level shape (object of sections → primitive leaves) rather than a fully general recursive JSON Schema walker — extend when a bot config actually needs deeper nesting. Save path is exactly the spec's words: validate (`ajv`, `src/lib/schema-validate.ts`) → write Postgres → publish `config.updated` on Redis (payload carries only the instance id — Postgres stays sole source of truth, publish failures are swallowed since "the loop makes it correct even if pub/sub drops," `specs/04-bot-runtime.md`). Token replace reuses `sealToken()` and never puts a token value in `instance_events`.

Two bugs the build/tests didn't catch, found only by driving the real flow end-to-end:
- `sealToken()`'s catch-all conflated "bad token format" with "server misconfigured" (e.g. `TOKEN_SEAL_PUBLIC_KEY` unset) into the same misleading "that token doesn't look right" message. Split into a distinguished `TokenFormatError`; anything else now surfaces as a real error instead of blaming the user for our config.
- The config form's `<input type="number" min max>` means real users can never submit an out-of-range value — the browser blocks it before JS or the server sees it. Server-side rejection of the same value is still covered (`schema-validate.test.ts` against the live schema), but that's now known to be a defense-in-depth backstop against a hostile client, not a path a real user can hit through the UI.

Verified with a real headless-Chromium run (Playwright driving system Chrome, not a mock) against live Postgres + Redis: full click-through — sign in, attest age, create instance, view schema-rendered defaults, save a config change, replace the token — then confirmed independently: the Redis subscriber actually received `config.updated`; Postgres held the submitted config verbatim; **a second signed-in user hitting the first user's `/instances/[id]` got a 404**, proving `getOwnedInstance`'s tenant scoping; and the replaced token's stored ciphertext was decrypted through the real `tokenbox.py` (separate process, separate keypair half) to the exact replacement value — the strongest possible proof the two-plane token design (`fd10d1a`) holds under a real write, not just the original cross-plane script's synthetic round trip.

## 2026-07-20 — Auth: Auth.js wired — Google OAuth + magic link, Node-runtime route gating
Auth.js v5 (beta) on the Drizzle adapter, against the auth tables built adapter-shaped from day one. Database-backed sessions, 30-day rolling (`updateAge` 24h). Both providers resolve to one `User` by verified email per the spec's linking rule — Google via `allowDangerousEmailAccountLinking` (safe here specifically because Google verifies email; the flag doesn't exist for the email provider, which unifies by construction since sign-in *is* an email lookup). Magic-link delivery (`src/lib/mailer.ts`) logs to console when `EMAIL_SERVER` is unset (dev) and throws if unset in production — no dedicated transactional-email provider chosen yet, that's still open. In-memory sliding-window limiter on the magic-link action (5/email, 20/IP per 15 min); flagged to swap for Redis before running >1 control-plane instance.

Route gating (`src/proxy.ts`) implements the spec's gating map as a pure classifier (`src/lib/route-access.ts`, unit tested) — public/auth/admin plus a separate age-attestation gate scoped to checkout + new-instance creation, not the whole dashboard, matching the spec's "purchase requires 18+" wording precisely. Landed on Next.js's new **Proxy** convention (`middleware.ts` renamed `proxy.ts`, per 16.2's deprecation) rather than the old name, since it's the same release we scaffolded on. Proxy always runs on Node.js (not Edge) — required here since `auth()` validates the database session against Postgres directly, which Edge can't do.

Verified end-to-end against live Postgres: full magic-link round trip (rate limit → CSRF → token issuance → console delivery → callback → session), single-use enforcement (replay correctly rejected), and all four gate outcomes (public passthrough, unauthenticated→`/login`, wrong-role→`/`, un-attested→`/account/attest-age`) exercised over HTTP against a running server, not just unit-tested in isolation. → `specs/06-auth.md`

## 2026-07-19 — Token encryption: libsodium sealed boxes, public-key-only control plane
Envelope/KMS deferred; v1 uses **sealed boxes** (X25519 + XSalsa20-Poly1305): control plane env holds only `TOKEN_SEAL_PUBLIC_KEY` — it can seal a pasted token but structurally cannot decrypt one; `TOKEN_SEAL_PRIVATE_KEY` lives only on data-plane hosts, unsealed at instance spawn (`token-seal.ts` / `tokenbox.py`, key-ref column for rotation, `keygen.py` per environment). Trial dedupe uses a peppered HMAC fingerprint (pepper control-plane-only). Cross-plane interop pinned by `scripts/check-token-seal.sh` + unit suites both sides (vitest is now the web test runner). → `specs/05-security.md`

## 2026-07-19 — ORM: Drizzle; initial Postgres schema landed
Drizzle over Prisma: schema-as-TypeScript colocated with the control plane, plain-SQL migrations the Python plane can read, no codegen step, lighter runtime for App Router. Initial schema (`apps/web/src/db/schema.ts`, migration `0000_init`): Auth.js-compatible `users`/`accounts`/`sessions`/`verification_tokens`; `catalog_bots` (slug PK, seeded with `emote`); `bot_instances` (token ciphertext/key-ref/last4/peppered-fingerprint — write-only per `05-security.md`; billing-owned `desired_state` vs. supervisor-observed `status` + `error_kind`); `subscriptions` (Stripe mirror, ours + raw status); `webhook_events` (raw archive, Stripe event id PK = idempotency); `trial_registry` (room + fingerprint, **no user FK** so dedupe survives account deletion, no PII); `instance_events` (append-only). Local dev via root `docker-compose.yml` (Postgres 17 + Redis 8). → `specs/02-architecture.md`
